8评测

这一章讲怎么给一个重建好的场景打分（设计文档第 9 节）。核心问题只有一个：每个真值物体，最后建好了、建坏了，还是漏了。

大白话

评测像阅卷。考生交上来的 .blend 是一张画在透明纸上的答卷，标准答案是另一张透明纸。

先把两张纸叠对齐，再按大小把题目分组，一道真值题配一个答案，最后每道题判"对、半对、没答"。叠纸的时候只能对准纸的边框（相机轨迹），不能拿答案本身去对，否则错的也会被对成对的。

8.1 评测流水线

从 .blend 到最后的图表一共六步。每一步的输入输出都写在箭头上。

评测流水线：从 .blend 到漏斗和前沿
  1. 导出预测框。评测脚本用 AHa-3D 自带的 export_model.py，从最终的 .blend 里导出每个语义根节点（按 instance_id 分组）的世界坐标有向框，写成 export/objects.json。P0 不经过 .blend 导出，直接写这个文件。
  2. 对齐。Pi3X 的坐标系和 CA-1M 的不一样。把两边的相机中心对应起来，解一个 Sim(3)（尺度、旋转、平移），加重力约束；另报一个尺度固定为 1 的 SE(3) 版本。见 8.2 节。
  3. 去结构件、分档。墙、地面、天花板、门框这些结构件不算物体，先去掉。剩下的按真值框最长边分成 XS、S、M、L 四档，每档报真值物体的数量。见 8.3 节。
  4. 一对一配对。用匈牙利算法把预测和真值一对一配起来，不看类别（CA-1M 有 48% 的框只写 "object"）。代价是按大小归一化的中心距离 d̂。
  5. 三种结局。每个真值物体归为建好了、建坏了、漏了之一。两套严格判据 I 和 D 分开，各出一张表。见 8.4 节。
  6. 汇总。画漏斗（第 5 章），做组间配对比较、按场景 bootstrap 的 95% 区间，最后画成本-精度前沿。见 8.5 节。
匈牙利算法是什么

它解的是"一对一分配"问题：给一张代价表（行是真值，列是预测），找一种配法，让每个真值最多配一个预测、总代价最小。

贪心地"每个真值挑最近的"会出问题：两个挨着的杯子可能抢同一个预测，另一个预测却没人要。匈牙利算法一次性看全局，不会出现这种情况。

8.2 为什么只用相机轨迹对齐

重建出来的场景在 Pi3X 自己的坐标系里，和真值差一个整体的缩放、旋转、平移。打分前要先把它挪到真值坐标系里。

挪的依据只能是相机轨迹，绝不能用被评测的物体。这是设计文档列的反目标之一。

具体做法是 Umeyama 算法：把 Pi3X 估的每帧相机中心 pᵢ 和 CA-1M 注册过的同一帧相机中心 qᵢ 配成对，求一个尺度 s、旋转 R、平移 t，让下面这个和最小。

min over s, R, t :   Σᵢ ‖ qᵢ − (s·R·pᵢ + t) ‖²

pᵢ ：Pi3X 估的第 i 帧相机中心
qᵢ ：同一帧在 CA-1M RT.json 里的相机中心（激光坐标系）
s  ：尺度；SE(3) 版本固定 s = 1
R  ：旋转；加重力约束（按我们的理解：只绕竖直轴转）
t  ：平移

旋转不受限时，它有闭式解（用一次 SVD），不用迭代，相当于轨迹评测工具 evo 里的 --align --correct_scale。

加了重力约束、只许绕竖直轴转时，旋转只剩一个角度，不能直接套那一步 SVD。按我们的理解，要改成只在水平面上求这个角（用 atan2），尺度和平移再跟着算，仍然是闭式解。

为什么还要报一个不修尺度的版本

Pi3X 给的是"近似米制"的点云，尺度可能偏。Sim(3) 会把这个偏差修掉，SE(3) 不修，两个一比就看得出 Pi3X 自己的尺度误差。

尺度误差会推着物体一起偏。03 号笔记的估算：全局尺度差 10% 时，离对齐中心 3 m 的物体会偏约 30 cm，形状再完美也算不上摆准。

手算 · 尺度差 10% 推着物体走多远

对齐中心在原点，一个物体的真实位置离原点 3 m。重建的尺度大了 10%，它就被放在 3 × 1.1 = 3.3 m 处。

偏差 = 3.3 − 3 = 0.3 m = 30 cm。对 8 cm 的杯子来说，这已经远远超出宽松门槛（见 8.4 节，d̂ ≤ 1 大约是 7 cm）。

容易搞错
  • VSI 开发集和 BVB 重新打分没有相机轨迹。只能退而用 L 档家具加地面来对齐，所以 L 档自己不打分，只给 XS、S、M 三档打分，表里注明。
  • 帧对应是现成的。输入 mp4 就是用 CA-1M 的帧合成的，Pi3X 抽到的每一帧都能找到对应的 CA-1M 帧（按我们的理解）。RT.json 只覆盖注册过的帧，没注册的帧不参与对齐。

这种"用轨迹对齐、再评物体"的做法有先例。SpatialLM 附录 C.3 先把 SLAM 估的相机轨迹对齐到真值轨迹，再评检测。

原文是 we align the estimated camera trajectory from MASt3R-SLAM to the ground-truth camera trajectory。

8.3 尺寸分档

按真值框的最长边分四档（设计文档 9.3 节）。每档都报真值物体的数量。

档最长边典型物体CA-1M 抽样里的框数
XS< 0.2 m杯子、鼠标、遥控器269
S0.2–0.5 m书、台灯、小盆栽、水壶363
M0.5–1.5 m椅子、床头柜、显示器、小书架285
L≥ 1.5 m沙发、床、桌子、柜子256（含结构件）
为什么按最长边，不按体积

薄物体按体积分会偏得很厉害。显示器约 0.6 × 0.05 × 0.4 m，体积只有 0.012 m³，按体积会被归成小物体；地毯长 2 m，体积也很小（03 号笔记的例子）。

03 号笔记没找到任何室内物体级重建论文按物体尺寸分档报 3D 指标，所以这套档是我们自己定义的，报告里要写明。

8.4 三种结局

配对之后，每个真值物体都要归进三种结局之一。判断顺序是一棵小决策树，点"下一步"一层一层看。

一个真值物体的三种结局
  1. 配上了吗。匈牙利算法给每个真值物体最多配一个预测，代价是 d̂ = ‖c_pred − c_gt‖ / r_gt，r_gt 是真值框的半对角线长。
  2. 严格判据。两套分开报。判据 I：IoU3D ≥ 0.25（另报 0.5），方便和前人比较。判据 D：d̂ ≤ 0.5，并且最长边之比在 0.67 到 1.5 之间。通过就是"建好了"。
  3. 宽松门槛。没过严格判据，但 d̂ ≤ 1.0 或 IoU3D ≥ 0.1，就是"建坏了"：东西建了，位置或尺寸不对。
  4. 漏了。根本没配上，或者配上了但连宽松门槛都没进。

为什么要两套判据？IoU 对小物体非常敏感，一点偏移就掉很多，而 d̂ 按物体大小归一化，大小物体一视同仁。3D-MOOD 也指出 IoU 对小物体和薄物体太苛刻，原文是 too restrictive。

手算 · 8 cm 的杯子偏 3 cm

假设：杯子当成边长 8 cm 的立方体；预测框和真值框一样大、都和坐标轴对齐；预测只沿一个轴偏了 3 cm。

  • IoU3D：重叠部分是 5 × 8 × 8 = 320 cm³；两个框各 512 cm³，并集 = 512 + 512 − 320 = 704 cm³。IoU = 320 ÷ 704 ≈ 0.455，从 1 掉了一半多。
  • d̂：半对角线 r = √3 × 8 ÷ 2 ≈ 6.93 cm。d̂ = 3 ÷ 6.93 ≈ 0.433。
  • 结论：0.455 ≥ 0.25，过判据 I；0.433 ≤ 0.5 且边长比为 1，过判据 D。两套都算"建好了"。

同样偏 3 cm，换成边长 2 m 的立方体：IoU = 197 ÷ 203 ≈ 0.970，d̂ ≈ 0.017。对大家具，3 cm 几乎没影响。

反过来算门槛。沿一个轴偏 x cm 时 IoU = (8 − x) ÷ (8 + x)，d̂ = x ÷ 6.93。

  • IoU 降到 0.25：x = 4.8 cm。
  • d̂ 到 0.5：x ≈ 3.46 cm。
  • d̂ 到 1.0：x ≈ 6.93 cm。这就是宽松门槛的边，因为 IoU ≥ 0.1 只撑到 x ≤ 6.55 cm，两者取"或"以宽的为准。
容易搞错
  • IoU 还看偏的方向，d̂ 不看。同样偏 3 cm，如果沿体对角线偏（三个轴各偏约 1.73 cm），IoU 只有约 0.317，d̂ 仍是 0.433。
  • 阈值都是我们定的初值。0.25、0.5、0.67–1.5、1.0、0.1 定死之前还没有任何 agent 运行，所以只在开发集上做两项合理性检查（设计文档 9.4 节）。
    • 真值对真值：应该全部"建好了"。
    • 检测器直接输出的框（Boxer 和干净对照）对真值：看分布合不合理。
    不拿任何 agent 组的输出来调阈值。10/20 前写进 configs/thresholds.json，之后不改。
  • IoU3D 的计算：03 号笔记建议用 pytorch3d.ops.box3d_overlap，输入是 8 个角点，顺序有规定，写脚本时要按文档排。

8.5 统计和成本

有了每个物体的结局，最后一步是比较各组，并且把钱算进去。设计文档 9.6、9.7 节定了四件事。

  • 配对比较。同一个真值物体在不同组里的结局两两对照，不只比总数。
  • 按场景 bootstrap。把 15 个测试场景有放回地重抽很多次，每次算一遍组间差，取中间 95% 作为置信区间。
  • 噪声底线。A1 和 A3v 在 5 个场景上各跑第二次，量出"同一组跑两次差多少"。组间差距比它小的，不下结论。
  • 成本。每次运行记 token 数（输入、缓存、输出）、按 API 价折算的美元、墙钟时间、fal 费用。
大白话

为什么按场景重抽，不按物体？同一个房间里的物体不是互相独立的：光线差、视频晃，整个房间的物体一起遭殃。按场景抽，才能把"碰巧抽到几个好拍的房间"这种运气算进区间里。

最后的结论写成成本-精度的帕累托前沿，不评"哪种最好"。横轴是每个场景花的钱，纵轴是小物体召回。

必记
  • 对齐只用相机轨迹（Sim(3) 加不修尺度的 SE(3)），绝不用被评测的物体。
  • 分档按真值框最长边：XS < 0.2、S 0.2–0.5、M 0.5–1.5、L ≥ 1.5 m。
  • 每个真值物体归为建好了、建坏了、漏了；判据 I 和 D 各报一张表。
  • 组间差要越过"同组跑两次"的噪声底线才下结论；结论写成成本-精度前沿。
  • 精确率（多建出来、对不上真值的物体）作次要指标。CA-1M 是穷举标注，这个数有意义。
  • 所有阈值 10/20 前写进 configs/thresholds.json 定死。

订阅不按次计费，所以成本轴要靠自己记 token 日志再按官方 API 价换算；价格和额度见第 9 章。
