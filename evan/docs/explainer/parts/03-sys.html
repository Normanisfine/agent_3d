3我们的系统架构

上一章是 AHa-3D 本身。这一章把它放进我们的整套系统里：什么在哪台机器上跑、文件怎么流、哪些东西所有实验组必须一样。

大白话

把整个项目想成一场厨艺比赛。

  • 备料只做一次。Betty 集群像中央厨房，把每个场景的“食材”（相机、点云、掩码、物体清单）一次备好，分装给所有参赛组。
  • 各组在同一个灶台上做。笔记本上的 AHa-3D 是灶台，同一把刀、同一口锅、同样的时限。
  • 评委只看成品。评测脚本拿真值（标准答案）打分，标准答案从头到尾不进厨房。

3.1 组件架构：两台机器之间只传文件

重活放在 Betty（学校的 GPU 集群，课程额度付费），要看图、要渲染的 agent 循环留在 Yifan 的笔记本上。两边之间只传文件。

Betty 的 B200 可以整卡用，也可以切成 MIG 切片用。MIG 是 NVIDIA 把一张大卡切成几块互相隔离的小卡；mig45 就是其中一块 45 GB 显存的切片，补贴价约是整卡的四分之一。

谁在哪跑，箭头上是传的文件
  1. Betty 上的感知。每个场景跑一次 Pi3X 和 SAM 3（作者默认的 32 帧、25.5 万像素），产出 bundle/。Boxer 在同样 32 帧的 1024×768 原图上检测，位姿和点图用 Pi3X 估的，产出 inventory.json。干净对照产出第二份清单 inventory_clean.json。
  2. AHa-3D harness。在笔记本上运行，原有工具和检查都不改，agent 由驱动模型扮演。主实验是 Codex CLI 加 GPT-6，开发和 5 个场景的复跑用 Claude Code 加 Opus 5.5。每次运行写一份 run_log.json。
  3. Blender。agent 写的 bpy 脚本在 Blender 5.2.1 后台运行，存成 scene.blend。Blender 只在笔记本上跑，因为 Betty 的 MIG 切片不支持图形接口。
  4. 我们写的工具。A3、A4 运行中由 agent 调 gen3d_request，把帧、掩码、点图交给 Betty 上的 SAM 3D，网格缓存到 gen/ 下（图里简写）。place_mesh 把网格配准进场景。细节在 第 6 章。
  5. P0 流水线。不经过 agent，也不调大模型。它用 Boxer 清单和干净对照清单各跑一遍，对每个框调同一套工具生成、摆放，过不了验收就用方块。最后自己写 scene.blend 和 export/objects.json。
  6. 评测脚本。从 agent 组的 scene.blend 导出每个物体的世界坐标框，写进 export/objects.json；P0 那一组直接用它自己写的。然后和 CA-1M 真值对齐、匹配，判三种结局，画漏斗，写进 results/。两份清单在“检测到”那一关也要读。评测细节在 第 8 章。
容易搞错
  • 订阅只能驱动 agent。ChatGPT 和 Claude Max 订阅给的是对话模型，跑不了 Pi3X、SAM 3D 这类 3D 模型。3D 模型只能在 Betty、笔记本或 fal 上跑。
  • SAM 3D 在笔记本上跑不了。官方要求至少 32 GB 显存，笔记本只有 12 GB。正式实验部署在 Betty；11 月 2 日前装不通，就改用笔记本上的 Hunyuan3D-2mini 加我们的配准。

设计文档第 3、6、7 节；调研笔记 04 第 1.8、1.10 节。

3.2 一个场景从头到尾

拿一个 CA-1M 场景走一遍。关键是第 2 步只做一次，第 3 步才按实验组分叉。

一个场景的七步：数据 → 感知 → 分叉 → 运行 → 生成 → 导出 → 评测
  1. 数据（Yujing）。把 CA-1M 的帧按 10 fps 合成 mp4 交给 AHa-3D，不下原始 .mov。22 个视频用固定种子分成 5 个开发、15 个测试、2 个备用，10 月 20 日前写进 configs/splits.json，之后不改。
  2. 感知（Mingjian，Betty）。Pi3X、SAM 3、Boxer、干净对照，每个场景只算一次，结果打包拷回笔记本。
  3. 分叉。七个实验组都读第 2 步的同一份结果，感知的随机性因此不会混进组间差异。P0 不调大模型，绕过第 4 步，直接进第 5 步。
  4. agent 运行（Yifan，笔记本）。每组每场景一次运行。所有组同一个墙钟上限、同一个轮数上限；跑崩或撞上限就重跑一次，还不行就拿最后存下的 .blend 打分，记为失败。
  5. 生成与摆放（Mingjian 的工具）。A3、A4 运行中由 agent 调用，P0 对每个框自动调用。生成在 Betty 上，配准在笔记本上，过不了验收门就退回方块。
  6. 导出（Yujing）。用 AHa-3D 的 export_model.py 按 instance_id 分组，导出每个语义根节点的世界坐标有向框，写进 export/objects.json。P0 直接写这个文件，不用导出。
  7. 评测（Yujing）。只用相机轨迹做 Sim(3) 对齐，匈牙利一对一匹配，每个真值物体判成“建好了 / 建坏了 / 漏了”，画漏斗，按场景 bootstrap 出置信区间。CA-1M 的真值只在这一步出现。
生成为什么不在 agent 的循环里卡住（按我们的理解）

gen3d_request 按“帧、掩码、后端、种子”缓存结果。P0 本来就要对每个 Boxer 框生成一遍，所以 A3 组请求同一个物体时，有可能直接命中缓存，不必等 Betty 排队。

能不能命中，取决于 A3 选的帧和掩码是否和 P0 一样。这一点设计文档没写，留给 Mingjian 实现时定。

设计文档也还没写两条和缓存有关的记账规则，我们建议这样定。

  • 命中缓存时，成本仍按一次生成记账。不然排在 P0 后面跑的生成组白占便宜，成本轴就不公平了。
  • 墙钟上限扣不扣等待生成的时间，和运行上限一起定。不管怎么定，所有生成组用同一条规则。

设计文档第 4、5、8、9 节。

3.3 “公平比较”的不变量

我们要说“A2 比 A1 好”，就得保证两组之间只差“有没有清单”这一处。下面这张表列出所有必须一样的东西。

不变量具体是什么为什么
感知结果每个场景在 Betty 上算一次 Pi3X 和 SAM 3（25.5 万像素、32 帧），所有组读同一份Pi3X 和 SAM 3 有随机性，重算会把这部分差异混进组间比较
AHa-3D 版本提交 82f4b11，或我们 fork 后的固定提交代码变了，结果就不可比
Blender5.2.1资产库用它保存
驱动模型和推理强度主实验同一个模型、同一个推理强度，全程不换换驱动会破坏“复现作者设置”这个前提（第 9 章）
墙钟和轮数上限所有组同一个值。第 1 周用 office48 只量额度；等 A1 在 3 个开发场景上跑出耗时和轮数的中位数（10/20–10/26 那周），取中位数的 2 倍，10/26 前写进 configs/run_caps.json“同样预算”就是靠这两个上限定义的
失败规则崩了或撞上限重跑一次；还不行拿最后的 .blend 打分，记失败。失败率每组单独报，配对比较不剔除防止某组靠“失败的不算”占便宜
原有功能可开合柜子、物理检查、审查门在所有组里照旧只比小物体处理方式
补丁如需打补丁，对包括 A0 在内的所有组一样；不允许人工干预人上手帮忙就无法复现

还有一条更根本的：真值传感器数据不进流程。CA-1M 带了激光深度和注册过的相机位姿，这些东西太准了，放进流程就不再是“单目视频进来”。

“高清帧”到底是什么
  • 帧。就是 Pi3X 用的那 32 帧，只是换成 CA-1M 的 1024×768 原图，没有多加帧。
  • 位姿。用 Pi3X 估的，不用 ARKit 的。
  • 深度。把 Pi3X 的点图放大到原图尺寸。SAM 3D 要的 pointmap 也从这里来。
  • 谁用。A2 起的 Boxer 检测和 A3 起的生成裁剪。高清帧消融就是把 A3v 换回 Pi3X 降采样后的帧，在 5 个场景上重跑。
估算 · 换成高清帧，小物体多出几个像素

算法：两种分辨率的边长比，按 1024 / 574 和 768 / 434 算。

  • 横向放大 1024 / 574 = 1.78 倍，纵向 768 / 434 = 1.77 倍，面积放大约 3.16 倍。
  • 一个在 Pi3X 帧里宽 20 像素的杯子，高清帧里约 20 × 1.78 = 36 像素宽。
  • 一块 100 像素的掩码，高清帧里约 100 × 3.16 = 316 像素。生成工具的门槛是约 200 像素（第 6 章），换帧前过不了，换帧后能过。

帧数没变，所以漏斗“看得见”这一关用的帧集合不变，只是多算一个分辨率。

容易搞错
  • Boxer 是“同源”的。Boxer 训练时用过 CA-1M 的训练集，在 CA-1M 上测会偏乐观。所以每张表都标“同源”，并放干净对照（SAM 3 掩码加 Pi3X 点云拟合框）。
  • 干净对照的范围有限。只在“检测到”这一关比较两种清单，P0 两种清单各跑一遍；agent 组只用 Boxer 清单，不重跑干净版。
  • 不能用被评测的物体做对齐。对齐只用相机轨迹，否则会把要测的误差抵消掉。
  • Pi3X 这一侧也可能沾了同源。它的前身 π³ 训练时用过 ARKitScenes（π³ 论文 §3.4），CA-1M 的视频就是 ARKitScenes；Pi3X 本身的训练集是否相同没核实。所以几何精度的绝对值可能偏乐观，报告里注明。所有组共用同一份感知结果，组间比较不受影响。

几个文件里面具体有什么（AHa-3D 代码里核实过的格式）
  • bundle/。Pi3X 的 inputs.npz（帧、帧号、时间戳）和 predictions.npz（点图、置信度、相机位姿、内参）；cameras.json（OpenCV 约定，世界系 Z 朝上）；SAM 3 的 masks.npz；TSDF 网格；地面和墙对齐后的相机。
  • mesh.glb。清理过的网格，Z 朝上、单位米、原点在底面中心。按（帧、掩码、后端、种子）缓存，多个候选分 c1、c2。
  • scene.blend。每个物体是一个带 instance_id 的根节点，导出脚本按它分组。
  • run_log.json。token 分输入、缓存、输出三类记，再按 API 价折成美元（设计文档第 9.7 节）。我们还建议记是否重跑、生成和摆放的每个决定，方便事后分析（设计文档没要求）。
容易搞错
  • 名字撞车。AHa-3D 的 X-Ray 工具 object_outline 也会写一个 objects.json，内容是逐物体轮廓。所以我们的导出放在 export/ 子目录里，免得被覆盖或读错。
  • bundle 要拷回笔记本。agent 的测量和叠图工具在笔记本上跑，读的就是 bundle/。每个场景的 bundle 有多大，第 1 周跑完第一个场景再量（见 第 9 章的硬盘一节）。
  • run_log 要从第一次运行就记。订阅不按次计费，事后补不回来。成本轴全靠它。
