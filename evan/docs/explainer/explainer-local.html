0.1 一支装修队：项目的整体样子

大白话

想象你请了一支装修队。任务是照着一段手机拍的房间视频，在电脑里把这间房原样搭出来，每件家具、每个杯子都要是能单独搬动的东西。

  • 视频就是房子的照片。手机绕房间慢慢走一圈，一个镜头拍到底。
  • 测量员是 Pi3X 和 SAM 3。Pi3X 算出每张照片是站在哪儿、朝哪拍的，以及画面里每个点离镜头多远；SAM 3 把照片里的地面、墙这些东西用荧光笔圈出来。他们每个房间只量一次，量完的数据留给全队共用。
  • 包工头是 agent，一个会用工具的大模型。它会看照片、会翻测量员留下的数据、自己在照片上量尺寸，也会写脚本搭家具，搭完还拿照片对一遍。
  • 定做小摆件的工厂是 3D 生成模型。寄一张杯子照片过去，工厂寄回一个杯子的 3D 模型。包工头可以自己拿方块拼杯子，也可以下单给工厂。
  • 验房是评测。拿激光扫描标出来的"真实户型图"（每件东西一个 3D 框），一件一件核对搭得对不对。

我们关心的是杯子、瓶子、书、遥控器、鼠标、台灯这些小东西。它们到底丢了多少、丢在哪一步，还没有人量过。我们要把这两件事量清楚，再看花多少钱补最划算。

真实的流程如下。共用感知的意思是，每个场景的 Pi3X 和 SAM 3 结果只算一次，所有实验组读同一份，这样感知环节的随机性不会混进组间差异。

agent 那一段跑在 AHa-3D 的 harness 里（套在大模型外面的工具和规则，见 1.7 节）。驱动模型是 GPT-6，通过 Codex CLI（OpenAI 的命令行 agent 工具）调用。

我们把 AHa-3D 原有的五个阶段归成四个环节：找物体、建形状、摆准、检查。所有改动都落在这四个环节里。

从一段房间视频到一张成本-精度图
  1. 房间视频进来。输入是一个连续镜头的房间视频。正式实验用 CA-1M 的帧按 10 fps 合成 mp4。AHa-3D 从里面均匀抽 32 帧，每帧缩到 25.5 万像素以内。
  2. 共用感知。Pi3X 估出每帧的相机（内参 K 和位姿 c2w，见 1.1 节）和近似米制的点图；SAM 3 分出地面、墙等的掩码。结果在 Betty 上算好（Penn 的 PARCC 计算集群，用课程额度，见 第 9 章），所有实验组读同一份。
  3. ① 找物体。先决定要建哪些东西。A0、A1 全靠 agent 自己看帧；从 A2 开始，agent 多拿到一份物体清单，是 Boxer 在高清帧上检测出的 3D 框和裁剪图。
  4. ② 建形状。agent 写 bpy 脚本（Blender 的 Python 接口，见 1.8 节），用方块、程序化柜子和资产库搭。从 A3 开始，小物体可以调 gen3d_request 交给生成模型。
  5. ③ 摆准。把形状放到对的位置、朝向和大小。agent 用 measure.py 在帧上量尺寸；生成出来的网格交给 place_mesh 配准（ICP 加剪影搜索，见 1.6 节）。
  6. ④ 检查。把场景的轮廓叠回视频帧（X-Ray），算掩码重合度；再查碰撞、支撑、稳定；最后由另一个只读的 Codex 会话当审查员，给出 accepted 或 rejected。没通过就回到 ② 改。
  7. 出场景，再评测。最终 .blend 里每个物体是一个语义根节点，导出它的世界坐标 3D 框。评测先用相机轨迹做 Sim(3) 对齐（旋转、平移加一个整体缩放，见 1.2 节），再用匈牙利算法一对一配对（一种求配对的算法，让一对一配上的总代价最小，见 1.9 节），把每个真值物体判成三种结局，画漏斗，最后和成本放在一起看（第 8 章）。
容易搞错
  • Pi3X 和 SAM 3 在 AHa-3D 里只管"大结构"。默认的 SAM 3 只分 person、glass、mirror、floor、wall，不会自动列出房间里有哪些物体。在 A0、A1 里，物体清单完全靠 agent 看帧来定。
  • "共用感知"是我们的设计决定。按我们的理解，作者的流程每次运行都会自己跑一遍参考构建；我们改成每个场景只算一次，是为了让组间差异只来自小物体的处理方式。

0.2 三个研究问题，以及各自怎么回答

整个项目只回答三个问题。每个问题对应一种测量和一张主图。

  • Q1 丢多少。以 AHa-3D 为代表的"视频转 3D 的 agent"，按物体大小分档，各丢了多少物体？
  • Q2 丢在哪一关。每个丢掉的物体，是画面里根本看不清、没被找到、没被建出来，还是建歪了？
  • Q3 怎么补最划算。流程的其他部分全部固定，只换小物体的处理方式，哪些做法落在成本-精度的前沿上？前沿上的做法，找不到别的做法比它又便宜又准（帕累托前沿，见 1.9 节）。

怎么回答 Q1。在 15 个 CA-1M 测试视频上，把每个真值物体判成"建好了、建坏了、漏了"三种结局之一，按真值框最长边分档（XS 小于 0.2 m，S 0.2–0.5 m，M 0.5–1.5 m，L 1.5 m 以上），每档报召回。

怎么回答 Q2。给每个真值物体记下它最远走到哪一关，每个实验组、每个尺寸档画一根堆叠条（第 5 章）。第一关"看得见"只用几何算，算出来就是"不管 agent 多聪明都过不去的天花板"。

怎么回答 Q3。七个实验组（第 4 章）共用同一份感知；六个 agent 组还共用同一个驱动和同样的时间、轮数上限；P0 不用大模型。各组只换小物体的处理方式。

成本用 token 日志按官方 API 价格折成美元，再加生成费。最后画帕累托前沿，不评"哪种最好"。

另外还有两个目标。一是大家具（L 档）不能比 AHa-3D 原版差；二是用 2 到 3 段自己拍的视频做定性展示。

一句话记住

Q1 看分档召回，Q2 看漏斗，Q3 看成本-精度前沿。七组共用同一份感知；六个 agent 组还共用同一个驱动和同样的时间、轮数上限；P0 不用大模型。

0.3 为什么值得做

理由有四条。前两条说明 AHa-3D 本身留了空白，后两条说明我们的贡献落在哪儿。

第一，AHa-3D 没有公布任何精度数字。它是一篇技术博客加一个开源仓库，用 GPT-6 Astra 驱动，把房间视频变成 Blender 场景。

博客只有并排对比视频和一张 token 表，没有任何精度数字。作者把消融（拿掉或换掉一个部件，看结果变多少）一节自己标成了占位。截至 10 月 14 日，仓库停在提交 82f4b11，没有评测脚本。

第二，从公开材料看，AHa-3D 对小物体的要求本来就放得很低。证据有四条，出处要分清。

  • 博客里一次对比实验（workflow ablation）给 agent 的任务，要求对上墙和主要家具，小物体近似即可。原文是 They should match the walls and major furniture and approximate small objects.
  • 仓库的精度档说明里，"Major objects"档写着桌面和柜顶的小摆设可以有出入。原文是 Small tabletop/cabinet-top decor may vary unless user-flagged。默认用的是哪一档，我们没有核实。
  • 资产库注册了 108 项，有蜡烛、花瓶、植物、餐具、挂画，没有杯子、书、遥控器这类常见的桌面物体。
  • 作者试过用 SAM 3D Objects 和 TRELLIS.2 生成物体，做完又搁置了，原因没公开。原文是 completed and then deferred。

第一条的出处要说准。"approximate small objects" 只出自那次对比实验的任务描述，不一定是发布版的默认提示词。所以 A0 原样跑作者的提示词，A1 另写一版"认真建小物体"的提示词当公平基线。

第三，"小物体交给生成模型"这个做法已经有人做了，所以它不是我们的贡献。下图列出五篇近期工作各自做了什么。

各家的分流方式也不一样，别记混。

  • GRASE（ICLR 2027 投稿）：大件用基本体搭，所有小件用 TRELLIS.2 生成。
  • LIVIN（arXiv 2610.12069）：按"能不能开合"分流。能开合的由 agent 写代码；所有不能开合的物体，包括大家具，都交给 Rodin 生成。
  • GATOR（arXiv 2610.11215）：每个物体都先生成，再交给 GPT-6 Astra 精修。
  • LiteReality-Agent（arXiv 2610.01863）：外观复杂、基本静止的物体走 TRELLIS.2。
  • CoDimRecon（arXiv 2609.36024）：容器里漏掉的小物体，用 SAM3D 补出来放回去。

所以我们的贡献是把账算清楚，具体是三点。

  1. 在"单目视频、整间房、agent 建模"这个设定下，第一次按物体大小分档，报召回和摆放精度。
  2. 把每个丢掉的物体归到具体哪一关丢的，也就是漏斗。
  3. 在同一套流程、同样预算下，比较几种小物体处理方式，同时报花了多少钱，画成本-精度曲线。

第四，"生成一定更好"本身就没定论。GATOR 给 GPT-6 Astra 每个物体 10 分钟，从零写代码建模，再和"先生成再精修"比。

比的指标是 Chamfer 距离：两个形状上的点互相找最近点，取平均距离，越小越像。两组数字的结论不一样。

验算 · 两组差距各是多少
  • ScanNet++：0.033 ÷ 0.031 ≈ 1.06，GPT-6 从零建的误差只多约 6%。
  • 桌面物体：0.016 ÷ 0.009 ≈ 1.78，误差多 78%，接近一倍。

只引其中一组都会误导人。引用时两组一起写。

一句话记住

"小物体交给生成"已经有五篇工作做过，我们的贡献是第一次把账算清楚：按大小分档、拆到每一关、同预算比做法和成本。"生成更好"是待检验的问题，结果是正是负都写进报告。

0.4 不做的事，以及哪些情况算失败

先划清边界。下面这些事我们明确不做。

不做的事
  • 不训练主线模型。训练只是加分项，10/26 决定做不做（第 14 章）。
  • 不量化形状和外观的好坏。CA-1M 只有框，形状只做定性展示；ScanNet++ 在 11/2 前批下来才补形状指标。
  • 不做动态物体、人体、室外。
  • 不重新实现 GRASE 或 GATOR 的整套系统。只借做法，比如 GATOR 式精修、GRASE 式剪影搜索。

还有四种情况，代码全跑通了也算失败。设计文档管它们叫"反目标"。下图把每一种画成一个小场景。

算失败的情况（反目标）
  • 实验组之间的差距小于同一组跑两次的差距，却写成了"某组更好"。A1 和 A3v 会在 5 个场景上各重复一次，专门用来量这个噪声。
  • 用被评测的物体去做对齐，把要测的误差抵消掉了。主口径只用相机轨迹做对齐。
  • 看了测试集结果再去调阈值或提示词。
  • 把 Boxer 在 CA-1M 上的结果当成泛化能力来报。所以每张表都放一个干净对照，用 SAM 3 实例掩码加 Pi3X 点云拟合有向框。它的检测部分没用 CA-1M 标注训练过；几何部分还有一处同源风险，见下一段。

干净对照的同源风险。Pi3X 的前身 π³ 训练时用过 ARKitScenes 和 ScanNet++（π³ 论文 §3.4），CA-1M 的视频就来自 ARKitScenes。所以几何的绝对精度可能偏乐观。

Pi3X 本身用没用过这些数据，还没核实。所有组共用同一份感知，组间比较不受影响。

必须记住的 5 件事
  1. 一句话：以 AHa-3D 为基线，第一次定量测出小物体丢了多少、丢在哪一步；再在同一套流程、同样预算下比较几种小物体做法的成本和精度。
  2. 四个环节：找物体、建形状、摆准、检查。Pi3X 和 SAM 3 的结果每个场景只算一次，所有组共用。
  3. 七个实验组：P0 不用大模型；A0 是作者原版；A1 要求认真建小物体；A2 加物体清单；A3r、A3v 加生成（按规则或由 agent 决定）；A4 加 GATOR 式精修。
  4. 评测：相机轨迹对齐，匈牙利一对一配对，每个真值物体判成建好、建坏、漏了；按最长边分 XS、S、M、L 四档；漏斗是主图。
  5. 结论怎么写："生成更好"是待检验的问题；差距小于同组重复的差距就不下结论；结果写成成本-精度的帕累托前沿。

1.1 相机：内参和位姿

大白话

拍照可以想成从一个小孔往外看。小孔后面一段距离放着底片，外面的东西沿直线穿过小孔，落在底片上。

  • 内参描述相机自己：底片离小孔多远（焦距），底片的中心在哪。人走到哪儿，内参都不变。
  • 位姿描述拍这一张时，相机站在房间哪里、朝哪个方向。手机绕房间走一圈，每一帧的位姿都不一样。

相机坐标系以相机中心为原点。按 OpenCV 的约定，Z 轴朝镜头看的方向，X 朝右，Y 朝下。一个点的 Z 值，就是它在镜头正前方多远，也叫深度。

针孔投影把相机坐标 (X, Y, Z) 变成像素坐标 (u, v)，公式只有两行。

u = f·X/Z + cx
v = f·Y/Z + cy
  • f 是焦距，单位是像素。
  • (cx, cy) 是主点，也就是光轴穿过画面的位置，通常接近画面中心。
  • 这三个数排成 3×3 的内参矩阵 K = [[f, 0, cx], [0, f, cy], [0, 0, 1]]。

关键在除以 Z。同一个杯子离得越远，Z 越大，在画面里就越小。

位姿写成一个 4×4 矩阵。AHa-3D 存的是 c2w（camera to world），它把相机坐标下的点变到世界坐标，世界坐标系 Z 朝上。反过来要把世界里的点投到某一帧，先乘 c2w 的逆，再套上面的公式。

Pi3X 从视频里同时估出每一帧的 K 和 c2w，AHa-3D 把它们写进 cameras.json。单位一栏写的是估计的米、没有标定，原文是 predicted metres; uncalibrated。

估算 · 2 米外的杯子在画面里有多大

杯子直径 8 cm、高 10 cm，离相机 2 m。另外假设相机水平视角 60°，这只是为了算数量级，真实值以 Pi3X 估出的 K 为准。

  1. Pi3X 用的帧：1024×768 的原图等比缩到 25.5 万像素以内，宽高再取 14 的倍数（Pi3X 的主干按 14×14 像素切块），约 574×434（574 × 434 = 249,116）。
  2. 焦距 f = (574 ÷ 2) ÷ tan 30° = 287 ÷ 0.577 ≈ 497 像素。
  3. 杯子在画面里高 497 × 0.10 ÷ 2 ≈ 25 像素，宽 497 × 0.08 ÷ 2 ≈ 20 像素。
  4. 换成 1024 宽的原图，f ≈ 512 ÷ 0.577 ≈ 887，杯子高约 44 像素，是前者的 1.78 倍。

提案里"2 米外 10 cm 的杯子只占二十来个像素"就是这么来的。项目里的"高清帧"也是这个道理：同样 32 帧，换回 1024×768 的原图（第 7 章）。

容易搞错
  • c2w 和 w2c 别用反。c2w 把相机坐标变到世界坐标，它的逆 w2c 才是把世界点变回相机。用反了，物体会跑到完全错的位置。
  • 不同软件的相机轴不一样。OpenCV 的相机朝 +Z 看、Y 朝下；Blender 的相机朝自己的 −Z 看、Y 朝上。同一个 4×4 矩阵换软件时，要先把轴转过来。
  • f 的单位是像素，和镜头上标的毫米焦距是两回事。图片缩小一半，f 也跟着减半。
一句话记住

内参管"怎么拍成像素"，位姿管"在哪拍、朝哪拍"；u = f·X/Z + cx，离得越远东西越小。

1.2 深度、点云和米制

大白话

深度图也是一张照片，只是每个像素记的是"这里离镜头几米"。

把每个像素沿着它的视线往外推这么远，就落在一个 3D 点上。整张图的点合在一起，就是点云。米制的意思是单位真的是米。

反投影就是把 1.1 节的投影公式倒过来用。知道像素 (u, v) 和深度 Z，就能解出这个点在相机坐标下的位置，再乘 c2w 进世界坐标。

X = (u − cx)·Z / f
Y = (v − cy)·Z / f
世界坐标 = c2w · [X, Y, Z, 1]ᵀ

点图（pointmap）是更直接的存法，每个像素直接存一个 3D 点。Pi3X 输出的就是每帧的点图、置信度和相机。

AHa-3D 再把各帧融合成一张网格。做法叫 TSDF（截断符号距离场）：把空间切成边长 3 cm 的体素（3D 里的小方格，相当于立体的像素），每格记下离最近表面多远，最后从这些距离里抽出表面。

米制指单位是真实的米。只靠单目视频，尺度在原理上定不下来：整间房放大一倍、相机也离远一倍，拍出来一模一样。

Pi3X 靠学到的常识估出一个大致的米，所以只能叫"近似米制"。

项目里用到点云的地方有四处。

  • agent 量尺寸。measure.py 让 agent 在帧上挑像素，从点图里读出 3D 点再算距离。端点置信度要不低于 0.5，3×3 像素块的 3D 跨度不能超过 0.12 m，否则拒绝。
  • SAM 3D 生成。可以把 Pi3X 的点图喂给它，喂了米制点图，它输出的位置和尺寸才是米制。
  • 干净对照。取 SAM 3 掩码里的点，拟合一个有向框（1.4 节）。
  • 评测。CA-1M 自带激光渲染的深度，只用来判断遮挡，不进流程。
手算 · 反投影一个像素，再看尺度误差有多伤

反投影。沿用 1.1 节的数，f ≈ 497，cx = 287，cy = 217。像素 (400, 217) 处的深度是 2.0 m。

  • X = (400 − 287) × 2.0 ÷ 497 ≈ 0.45 m，Y = (217 − 217) × 2.0 ÷ 497 = 0，Z = 2.0 m。
  • 这个点在镜头正前方 2 米、往右 45 厘米。

尺度误差。假设整个重建大了 10%，把它简化成从对齐中心往外的整体放大。离中心越远，被推得越远。

  1. 离对齐中心 3 m 的杯子被推到 3 × 1.1 = 3.3 m，挪开 0.3 m，约 30 cm。
  2. 杯子 8×8×10 cm，半对角线 r = ½ × √(0.08² + 0.08² + 0.10²) ≈ 0.075 m。
  3. 按大小归一化的中心距离 d̂ = 0.30 ÷ 0.075 ≈ 4.0。严格判据要 d̂ ≤ 0.5，也就是中心差在 3.8 cm 以内；宽松门槛是 d̂ ≤ 1.0。
  4. 两道线都没过，形状再完美的杯子也被判成"漏了"。

所以评测的主口径用 Sim(3) 对齐（旋转、平移加一个整体缩放），顺带把尺度修正掉。另报一个 SE(3) 版本（只有旋转和平移，不带缩放，尺度固定为 1），专门体现 Pi3X 自己的尺度误差（第 8 章）。

容易搞错
  • 深度 Z 是沿光轴的距离，和点到相机中心的直线距离不同。画面边上的点，两者差得最多。
  • 点云密不代表尺度准。Pi3X 的点云可以很密、形状很像，整体却大了或小了一圈。
  • 小物体在点图里只有几百个点。上面那只杯子在 Pi3X 帧里约 20×25 像素，边缘那一圈的点还最不可靠。
  • Pi3X 的几何可能也沾了同源。它的前身 π³ 训练时用过 ARKitScenes（π³ 论文 §3.4），CA-1M 的视频就来自 ARKitScenes，所以几何的绝对精度可能偏乐观。Pi3X 本身用没用过还没核实。所有组共用同一份感知，组间比较不受影响。
一句话记住

像素、深度、内参三样一起，反投影成相机坐标下的点，再乘 c2w 进世界；单目估出的米只是近似，整体差 10%，3 米外的杯子就被推出判定圈。

1.3 分割和掩码

大白话

拿荧光笔把照片里的杯子涂满，别的地方不涂。涂了的格子记 1，没涂的记 0，这张 0/1 表就是杯子的掩码。

SAM 3 是一个会听指令涂色的助手。你说"杯子"，它就把每个杯子各涂一张；你没提到的东西，它不涂。

掩码（mask）是一张和原图一样大的表，每个像素只有 0 或 1。分割就是算出这张表。分割有两种粒度。

  • 语义分割只分类别，所有杯子涂成一块。
  • 实例分割还分个体，1 号杯子和 2 号杯子各一张掩码。

SAM 3 能按文字提示做实例分割。给它 "cup"，画面里每个杯子各出一张掩码。

AHa-3D 默认只给 SAM 3 五个提示词：person、glass、mirror、floor、wall。它逐帧分割，阈值 0.3，同一类的实例合成一张，也不跨帧追踪。这些掩码主要拿来拟合地面和墙。

仓库里有物体级的 SAM 3 工具，但默认流程不会调用。原文是 not invoked automatically by the shared scene workflow。

我们在三个地方要用到物体级的掩码。

  • 干净对照。SAM 3 实例掩码加 Pi3X 点云，拟合每个物体的有向框，用来和 Boxer 的清单比。
  • 生成。SAM 3D 要整张图加这个物体的掩码，它直接把图乘上掩码，掩码画歪了生成也跟着歪。gen3d_request 在最好那一帧的掩码不足约 200 像素时，直接返回 too_small。
  • 剪影匹配。拿掩码和模型投影出的轮廓比重合度（1.6 节）。
估算 · 杯子的掩码有几个像素

沿用 1.1 节的假设（Pi3X 帧约 574×434，f ≈ 497），按外接矩形估面积。

  • 2 m 外：约 20 × 25 ≈ 500 像素。过得了漏斗"看得见"的 100 像素门槛，也够生成工具的 200 像素下限。
  • 4 m 外：边长减半，约 10 × 12.4 ≈ 120 像素。还算看得见，生成工具却会返回 too_small（A3 实际在高清帧上生成，这正是高清帧消融要量的情况）。
  • 同样 4 m，换成 1024×768 的高清帧（f ≈ 887）：约 17.7 × 22.2 ≈ 390 像素，又够生成了。
容易搞错
  • SAM 3 只分你点名的东西。AHa-3D 的默认名单里没有任何物体类别，所以 A0、A1 的物体清单全靠 agent 看帧来定。
  • 同一个杯子在不同帧是不同的掩码。AHa-3D 默认不做跨帧关联，要把多帧的掩码对到同一个物体上，得另外做。
  • 掩码面积跟着分辨率变。同一个杯子，帧越小面积越小。漏斗里"看得见"按各组实际用到的帧算：A0、A1 按约 574×434 算；P0 和 A2 起用同样 32 帧的 1024×768 原图，按原图算。
一句话记住

掩码是和图一样大的 0/1 表；SAM 3 按文字提示分割，没点名的不分；AHa-3D 默认只点名 5 类，杯子不在其中。

1.4 3D 框（有向包围盒）

大白话

给每件东西套一个刚好装下它的纸箱。纸箱放在哪、多大、转了多少度，这几个数就说清了这件东西在房间里占的地方。

验房时不看杯子长什么样，只看纸箱摆得对不对。

有向包围盒（oriented bounding box，OBB）用三组数描述。

  • 中心 c = (x, y, z)，3 个数。
  • 尺寸 (l, w, h)，长、宽、高，3 个数。
  • 朝向。只绕竖直轴转时是 1 个角，叫 yaw（偏航角）。

合起来 3 + 3 + 1 = 7 自由度。如果允许任意转动，朝向要 3 个角（yaw 加俯仰、侧倾），就是 9 自由度。

家具和桌面上的东西大多正放，只绕竖直轴转。CA-1M 的世界坐标框存了完整的 3×3 旋转和 8 个角点，Z 朝上。

抽查 6 个视频共 1,173 个框，带俯仰或侧倾的只有 24 个，约 2%。CA-1M 论文训练和评测也用重力对齐的 7 自由度框。

分档看最长边。项目按真值框的最长边分四档：XS 小于 0.2 m，S 0.2–0.5 m，M 0.5–1.5 m，L 1.5 m 以上。

上面那 1,173 个框里，XS 占 22.9%，S 占 30.9%，M 占 24.3%，L 占 21.8%。L 档里有墙、门框这类结构件，评测前要去掉。

项目里的框有三个来源。

  • 真值。CA-1M 的标注，每个视频约 125 个框，不分类别。
  • 预测。从最终 .blend 里每个语义根节点导出世界坐标的有向框（1.8 节）。
  • 清单，有两种。
    • Boxer 是开放词汇的 3D 框检测器，分两步出框。先用 OWLv2 按文字提示在图上找 2D 框（也可以直接喂外部的 2D 框），再结合相机位姿、内参和重力方向（深度可选）把 2D 框抬成 3D 框。
    • 干净对照取 SAM 3 掩码里的点，做主成分分析（PCA：找出这团点散得最开的几个方向，当作框的轴），再沿这些轴量出框的大小。
手算 · 几样东西落在哪一档
  • 杯子 8×8×10 cm：最长边 0.10 m，XS。半对角线 ½ × √(0.08² + 0.08² + 0.10²) ≈ 0.075 m，1.2 节和 1.9 节都用到它。
  • 一本书 24×17×3 cm：最长边 0.24 m，S。
  • 一张书桌 1.6×0.8×0.75 m：最长边 1.6 m，L。
容易搞错
  • 框不等于形状。一只杯子和同样大小的方块，框一模一样。CA-1M 只有框，所以我们只评位置和大小，形状只做定性展示。
  • 长宽和 yaw 绑在一起。长宽对调、再转 90°，是同一个框。比较朝向时要考虑这种等价；圆杯子这类对称物体，朝向本来就没有意义。
  • 分档只看最长边。台灯再细，高过 0.5 m 就进 M 档。显示器多数也在 M 档，别拿它当小物体的例子。
一句话记住

3D 框 = 中心 3 + 尺寸 3 + yaw 1 = 7 个数；CA-1M 的框几乎都只绕竖直轴转；按最长边分 XS、S、M、L 四档。

1.5 图生 3D 和"规范空间"

大白话

给工厂寄一张杯子照片，工厂寄回一个杯子模型，连看不到的背面都补好了。

多数工厂寄回的是"标准件"：统一缩到一个小盒子里、摆正。它原来在你家桌上的哪个位置、朝哪边、有多大，工厂一概不管，得你自己摆。

SAM 3D 这家工厂会顺手附一张摆放说明，写着该转多少、挪多少、放大多少。

图生 3D：输入一张图和物体的掩码（或去掉背景的裁剪图），模型生成完整的网格。看不到的部分，靠训练时学到的先验来猜。

规范空间（canonical space）是生成器自己的标准坐标系。Hunyuan3D、TRELLIS 这类模型输出的网格缩放进单位大小的盒子；02 号笔记推断它们一般是正放的，但朝前的方向、真实尺寸和位置都不知道。

要把这样的网格放进房间，还得自己求大约 7 个数：平移 3 个、yaw 1 个、尺寸 1 到 3 个，外加"哪条轴朝上"这个离散的歧义。这一步交给 place_mesh（1.6 节）。

SAM 3D Objects 走的是另一条路。它吃整张图加掩码，还可以加 Pi3X 的点图；输出网格的同时，直接给出相机坐标下的旋转 R、平移 t、尺度 s。再乘上 Pi3X 给的 c2w，就到了世界坐标。

它发布的代码里，refine_scale 把三个轴的尺度取平均。也就是说尺度只有一个数，是各向同性的。

几个有出处的数字。

  • 形状。在真实、杂乱、带遮挡的物体上，SAM 3D 的 Chamfer 是 0.0400，Hunyuan3D-2.0 是 0.0866，TRELLIS 是 0.0902，越小越好（SAM 3D 论文表 2）。
  • 位姿。比的是 3D IoU（两个框重叠体积的比例，见 1.9 节）。SAM 3D 自己预测的位姿是 0.4254；Hunyuan3D-2.0 生成后再用 FoundationPose（NVIDIA 的物体位姿估计模型，给定网格估 6 自由度位姿）估位姿，只有 0.2937。出处是同一论文表 3，测试集 SA-3DAO（论文用的真实场景物体测试集，只给 RGB）。
  • 算力。SAM 3D 官方要求至少 32 GB 显存；在 A100 上约 13 秒一个物体，进程占 22 GB。Hunyuan3D-2mini 只生成形状，官方要 6 GB。

所以正式实验把 SAM 3D 部署在 Betty 上，用课程额度。Yifan 的笔记本只有 12 GB，先用 Hunyuan3D-2mini 在本地把 gen3d_request 和 place_mesh 写通。

fal 上的 SAM 3D 自费不超过 10 美元，只用来核对位姿的坐标约定。11/2 前 Betty 装不通，正式实验就改用本地 Hunyuan3D-2mini 加我们的配准。

AHa-3D 作者自己试过 SAM 3D Objects 和 TRELLIS.2，做完又搁置了，生成适配器没有随仓库发布，原因没公开。

生成器实际看到多少像素

生成器都会把物体裁出来，再缩放到固定大小。一个 60×60 像素的杯子，按 02 号笔记读预处理代码后的推算如下。

  • TRELLIS：裁出约 72 像素，放大约 7 倍到 518。
  • TRELLIS.2：放大约 17 倍到 1024。
  • SAM 3D：物体那一路放大约 8 倍到 518。

放大不会凭空多出细节，模型真正拿到的信息就是那 60 个像素宽的一块。所以小物体要尽量从高清帧上裁。

容易搞错
  • 各向同性的尺度修不了比例。生成的瓶子如果比真瓶子矮胖，一个统一的 s 只能整体放大缩小。照 GRASE 的做法，place_mesh 的剪影搜索把长宽高三个尺寸分开调，可以再修一次。
  • 订阅跑不了生成模型。ChatGPT 和 Claude Max 订阅只能驱动 agent。3D 生成要么在 Betty、笔记本上自己跑，要么在 fal 上按次付费。
  • 生成得好看不等于摆得准。评测只看框的位置和大小，摆歪了的漂亮网格照样算建坏了。
  • 许可。Hunyuan3D 的许可排除欧盟、英国、韩国；按我们的理解不影响美国的课程项目。
一句话记住

规范空间的生成器只给形状，位置、朝向、尺寸要自己配准；SAM 3D 直接给相机系下的 R、t、s，但尺度是一个数（各向同性），而且要 32 GB 显存。

1.6 配准：ICP 和剪影匹配

大白话

配准就像把一张透明描图纸盖在照片上，来回挪、转、放大缩小，直到两边的线对上。

  • ICP 是拿点对点去对：每个观测点找描图纸上最近的点，再整体挪一下，让大家都更近。
  • 剪影匹配是比影子：把模型投到截图上，看投出的轮廓和掩码重合了多少，再一点一点试着调。

ICP（iterative closest point，迭代最近点）反复做两件事：先配对，再求一个让配对点整体最贴近的旋转 R 和平移 t。

E(R, t) = Σᵢ ‖R·mᵢ + t − oᵢ‖²

oᵢ 是第 i 个观测点，mᵢ 是模型上离它最近的点。固定配对时，最小化 E 的 R 和 t 可以直接用公式一步算出。挪完以后最近点会变，所以要重新配对，一轮一轮做下去。

ICP：配对、整体挪动、再配对
  1. 观测点。相机只看到物体的左面和下面（实心点），这些点来自 Pi3X 的点云，背面是空的。
  2. 模型的起点。生成的网格是完整的（空心点），先放在一个初始位姿上，比如 SAM 3D 给的位姿，或者 3D 框。这里故意让它偏了一些、还转了 20°。
  3. 配对。每个观测点找模型上离它最近的点（蓝线）。起点偏的时候，有些配对是错的，比如左面的观测点连到了模型的左上角。
  4. 求 R、t。在这组配对下，算一个让距离平方和 E 最小的旋转和平移，把模型整体挪过去（红箭头）。
  5. 重复到收敛。挪完重新配对、再挪，直到 E 几乎不再变小。GRASE 的设置是阈值 1e-5、最多 25 轮。起点太远时，错的配对会把模型带到一个错的位置，算法也会停下来，以为自己对齐了。

剪影匹配换了一个比较方式。把模型按某一帧的相机渲染出轮廓，和这一帧的掩码比重合度。

IoU = 交集面积 / 并集面积

GRASE 用的这个目标要先渲染出轮廓、再数像素算 IoU，不可微，没法顺着梯度走。它的做法是有界坐标搜索。

  • 一次只动一个参数，往两边各试一步，变好就挪过去。
  • 一层一层把步子缩小。
  • 参数只在一个有限范围里找。
手算 · 剪影 IoU 和验收线
  1. 掩码 400 像素，模型渲染出的剪影 360 像素，两者重叠 300 像素。
  2. 并集 = 400 + 360 − 300 = 460，IoU = 300 ÷ 460 ≈ 0.65。
  3. place_mesh 的剪影验收线是 max(0.6, 方块版 IoU + 0.03)，IoU 取多帧平均。假设同一个物体用方块代替时 IoU 是 0.55，线就是 max(0.6, 0.58) = 0.6，这一项过了。
  4. 另外还有三项：观测点到网格的 Chamfer ≤ max(1.5 cm, 0.1 × 最长边)；尺寸在框的 0.75 到 1.25 倍之间；穿进支撑面不超过 1 cm。四项都过才保留网格，否则退回方块。

再看小物体有多敏感。20×20 像素的掩码，同样大小的剪影偏 5 像素，交集 15 × 20 = 300，并集 800 − 300 = 500，IoU = 0.6，正好压在验收线上。

深入：GRASE 的剪影搜索参数

GRASE 附录 A.3 和表 3 的设置，我们的 place_mesh 照它实现。

  • 要调的参数：水平位置 2 个、绕支撑面法向的 yaw、三个尺寸；底面高度由支撑面决定。
  • 目标函数：各视角 (1 − 掩码 IoU) 加边界距离的平均，加最差视角一项，加点到面距离一项；后三项的权重是 0.4、0.35、0.12（边界、最差视角、点云）。
  • 搜索：不求导，有界坐标搜索，3 层，每层 4 遍，三层的步长依次是 1、0.5、0.25。这是归一化后的单位。位置范围只有 ±0.18 × 最长边，步长 1 若按米算会直接跳出范围；按我们的理解是相对可调范围的比例，实现前对照原 PDF 核实。
  • 范围：位置约 ±0.18 × 最长初始边，yaw ±0.45 rad，尺寸 0.75 到 1.25 倍。
  • ICP：收敛阈值 1e-5，最多 25 轮；每次内层求解约 50 次函数评估。

这些常数是从 PDF 抽出的文字里读的，排版有错位，实现前要对照原 PDF 再核一遍。

容易搞错
  • ICP 要一个好起点。起点差太远，最近点会配错，算法停在错的位置还以为收敛了。所以 place_mesh 先用 SAM 3D 给的位姿或 3D 框当起点。
  • 一个视角的剪影管不住前后。物体沿视线前后挪一点，剪影几乎不变，所以 IoU 要多帧平均，还要配合点云那一项。
  • 验收是和方块比。网格的剪影 IoU 要比同一位置的方块高 0.03 以上，才算"生成值得"。
一句话记住

1.7 agent、harness 和驱动模型

大白话

还是那支装修队。

  • agent 是包工头。它会看图纸、会叫师傅来量、自己也动手，干完一步看一眼结果，再决定下一步。
  • harness 是装修公司的工具箱和规章。能用哪些工具、每一步要交什么检查、什么时候算完工，都写在里面。
  • 驱动模型是包工头的脑子。同一套工具箱和规章，可以换一个人来当包工头。

agent 是在循环里调用工具的大模型。它读截图或工具输出，想下一步，调一个工具（运行命令、写 bpy 脚本、渲染一张图），读结果，再想。直到满足停止条件为止。

harness 是包在模型外面的一切：工具、提示词和技能文件、检查步骤、停止规则、轮数和时间上限。AHa-3D 本身就是一个 harness。

驱动模型是循环里那个大模型。作者用的是 GPT-6 Astra，推理强度 medium。

agent 的循环和 harness 的边界
  1. 看。agent 先看材料：视频帧、参考视角的叠加图，或者上一轮渲染出的场景截图。
  2. 想。驱动模型决定下一步，比如在哪一帧挑两个像素量书桌的宽，或者哪个物体歪了要改。
  3. 调工具。执行命令或写 bpy 脚本。常用的有 measure.py 量尺寸、roomkit.py 搭东西、source_fit 算掩码重合度、check_placement 查物理，最后由 codex exec --image 起一个只读审查员。
  4. 看结果，再想。读工具的输出，比如测量值、report.json、叠加图，回到第 2 步。循环到审查员给出 accepted，或者撞上轮数、时间上限为止。
  5. harness 的边界。外框里是工具箱和规则。审查门、物理检查、Stop hook（agent 想收工时先跑的检查，重建没完成就不让它停）都是 AHa-3D 自带的，在所有实验组里保持一样。轮数和墙钟上限是我们加的，所有组用同一套。各组改的是提示词、物体清单和新增的生成工具（第 4 章）。
  6. 驱动可换。主实验用 Codex CLI 驱动 GPT-6，订阅里有 Astra 就用 Astra，没有就用 Sol。开发调试和 5 个场景的复跑，用 headless Claude Code 驱动 Opus 5.5。

驱动模型对结果影响很大。Agentic RSR（arXiv 2610.10479）的 v2 版在同一个 harness、18 个 Blender 场景上比较了八个驱动。

这个 harness 叫 DSH，论文里的全称是 DeepSeek Harness。论文特意说明它和表里测的 DeepSeek 模型是两回事。

容易搞错
  • 主实验不换驱动。AHa-3D 是在 GPT-6 Astra 上调出来的，换驱动会破坏"复现作者设置"这个前提。额度不够时宁可少跑场景。
  • Opus 5.5 只是"能跑"。README 说它能驱动这个仓库，但没充分测过。原文是 Opus 5.5 can also drive this repository based on initial experiments, but it has not been fully tested。
  • 审查员写死了 Codex。审查步骤调的是 codex exec --image。Claude 驱动时要加一个转发 shim（冒充 codex 命令的小脚本，把审查请求转给 Claude），之前的会话里做过。
  • 同一组跑两次结果也不同。大模型有随机性，所以 A1 和 A3v 在 5 个场景上各重复一次，专门量这个噪声。
  • 订阅不按次计费。成本轴要靠 token 日志，按官方 API 价格折成"API 等价美元"。

1.8 Blender 和 bpy

大白话

Blender 是一个免费的 3D 软件，平时用鼠标拖。bpy 是它的 Python 接口，一行代码就能放一个方块、挪一个位置。

agent 没有鼠标，所以它写 bpy 脚本。好处是场景完全可编辑，每个物体都是独立的对象。

Blender 里的东西组织成一棵树，每个对象可以有父对象。Empty 是没有几何形状的对象，常拿来当一组东西的"把手"。

AHa-3D 规定，每个物体是一个语义根节点：一个 Empty，带着几个自定义属性，下面挂可替换的子网格。

  • instance_id：这个物体的编号，全场景唯一。
  • semantic_class：类别，用斜杠路径写，比如 furniture/... 这样。
  • support_id：按字面理解，记的是它放在哪个物体上。

评测正是靠这个结构。export_model.py 按 instance_id 把子网格分组，我们再给每个根节点算一个世界坐标的有向框。

下面这段 bpy 建一个杯子大小的方块，并挂到它自己的根节点下。AHa-3D 的 agent 实际调用的是 roomkit.py 里的 box() 等函数，它们在底层做的是同类的事。

import bpy

# 1. 建一个边长 1 m 的方块，再按米缩放成杯子大小
bpy.ops.mesh.primitive_cube_add(size=1, location=(1.2, 0.4, 0.80))
cup = bpy.context.object
cup.scale = (0.08, 0.08, 0.10)      # 长、宽、高，单位米

# 2. 建一个 Empty 当语义根节点（放在原点），写上编号
root = bpy.data.objects.new("cup_03", None)   # None 表示没有几何，就是 Empty
bpy.context.collection.objects.link(root)
root["instance_id"] = 17
cup.parent = root

桌面高 0.75 m，杯子高 0.10 m，所以杯子中心放在 0.80 m。Blender 的长度单位默认是米，Z 朝上。

AHa-3D 要求 Blender 必须是 5.2.1，因为它 41 MB 的资产库是用这个版本保存的。

容易搞错
  • 方块默认边长是 2 m。primitive_cube_add 不写 size=1 的话，方块边长是 2 m，同样的 scale 会建出 16×16×20 cm 的"杯子"。
  • 小物体要挂在自己的根节点下。placement 检查只对带 instance_id 的根节点做稳定性仿真，没有的只查碰撞和支撑；评测也按根节点导出框。agent 新建的小物体不挂根节点，就可能算不进去。
  • 版本要对。资产库是 5.2.1 保存的，换别的版本可能读不对。做人体动作要另装 Blender 4.5，我们用不到。
一句话记住

bpy 用代码建物体；AHa-3D 的每个物体是一个带 instance_id 的 Empty 根节点加子网格，评测从根节点导出 3D 框；Blender 必须是 5.2.1。

1.9 评测里的几个词

大白话

验房要用到四件工具。

  • IoU 量两个纸箱重叠了多少。
  • 匈牙利配对把"建出来的"和"真值"一一对上号，一个真值只认一个。
  • bootstrap 把验过的房子重新抽几遍，看结论稳不稳。
  • 帕累托前沿找出"又便宜又好"的那几家，被别人全面压过的不用再看。

IoU（交并比）= 交集体积 ÷ 并集体积，1 是完全重合，0 是不挨着。判据 I 要求 IoU3D ≥ 0.25，另报 0.5。

小物体在 IoU 下很吃亏，所以还有判据 D：按大小归一化的中心距离 d̂ = ‖c_pred − c_gt‖ / r_gt ≤ 0.5，r_gt 是真值框半对角线长，并且最长边之比在 0.67 到 1.5 之间。两套判据分开报。

匈牙利算法在一对一的约束下，让配对的总代价最小。代价就是 d̂。配对不看类别，因为 CA-1M 有 48% 的框类别只写了 "object"。

bootstrap 对 15 个测试场景有放回地重抽，每抽一次重算一遍指标，看结果晃多少，得出 95% 置信区间。比较两组时，同一个真值物体在两组的结局两两配对再算差值。

帕累托前沿：在成本和精度两个维度上，没有被别的做法"又便宜又准"同时压过的那些点。结论写成前沿，不写"哪种最好"。

手算 · IoU 和贪心配对

IoU。杯子 8×8×10 cm，体积 640 cm³。预测往一侧偏 s cm，交集是 (8 − s)×8×10。

  • s = 2：交集 480，并集 1280 − 480 = 800，IoU = 0.60。
  • s = 4：交集 320，并集 960，IoU ≈ 0.33。
  • s = 4.8：交集 256，并集 1024，IoU = 0.25，刚好压线；再偏一点就不过判据 I。
  • 对照：2×0.9×0.8 m 的沙发顺长边偏 4.8 cm，重叠比例 (2 − 0.048) ÷ 2 = 0.976，IoU = 0.976 ÷ (2 − 0.976) ≈ 0.95。

匈牙利对贪心。用图里那张 3×3 的 d̂ 表。

  • 贪心：先拿最小的 P1–G1 = 0.2；剩下 P2、P3 对 G2、G3，再拿 P3–G3 = 0.4；P2 只能配 G2 = 1.5。总代价 2.1，P2–G2 超过宽松线 1.0，G2 会被判成"漏了"。
  • 匈牙利：P1–G2 = 0.3，P2–G1 = 0.3，P3–G3 = 0.4，总代价 1.0。三对都 ≤ 0.5，都能进严格判据 D 的距离线。
容易搞错
  • bootstrap 按场景抽，不按物体抽。同一个场景里的物体互相关联（同一段视频、同一次重建），按物体抽会把区间算得太窄。
  • 区间要和噪声地板一起看。组间差距小于同一组跑两次的差距，区间再窄也不下结论。
  • 阈值是我们定的初值。0.25、0.5、0.67–1.5 这些数 10/20 前定死，之后不改。定之前只在开发集上做两项合理性检查：真值对真值，以及检测器直接输出的框对真值；不拿任何 agent 组的输出来调。
一句话记住

IoU 量重叠，对小物体很苛刻，所以另有 d̂ 判据；匈牙利让一对一配对的总代价最小；bootstrap 按场景重抽算置信区间；结论画成成本-精度的帕累托前沿。

大白话

  • 他先请测量队（Pi3X、SAM 3）把视频过一遍，拿到每个机位在哪、房子大概多大。
  • 他自己拿尺子在照片上量（measure.py），再亲自动手搭（写 Blender 脚本）。

2.1 五段流程：观察、测量、搭建、检查、审查

整条流程分五段。第一段是一条命令自动跑完的；测量、搭建、检查由 agent 主导，它看图、调工具、写脚本；审查交给另开的一个会话，审查员点头才算完。

先认识几个名词，下面的图里都会出现。

  • Pi3X。一个前馈 3D 重建模型。喂进一组视频帧，一次算出每帧的相机位姿和每个像素的 3D 坐标（点图）。
  • SAM 3。Meta 的分割模型。给一个文字提示（如 floor），它把图里对应的区域涂出来，这块区域叫掩码。
  • RANSAC。一种拟合方法。反复随机抽几个点拟合平面，留下最多点支持的那个，所以不怕杂点。
  • TSDF。把很多帧的深度融合成一张表面网格的老方法。AHa-3D 用 3 cm 的体素格子。
  • bpy。Blender 的 Python 接口。agent 写的“建模代码”就是 bpy 脚本。
AHa-3D：从一段视频到一个能交给仿真器的 .blend
  1. 观察（Observe）。一条命令跑完。Pi3X 均匀抽 32 帧，每帧缩到不超过 255,000 像素，估出相机和点云。SAM 3 分出地面、墙等五类，RANSAC 拟合地面和墙，再融合成 3 cm 的 TSDF 网格。agent 只负责执行和目视检查。
  2. 测量（Measure）。agent 在某一帧上挑像素点，写进一个 spec 文件，调 measure.py 读回米制数字。量法有水平距离、三维距离、中位高度、竖直距离四种，不可靠的端点会被拒绝。
  3. 搭建（Build）。agent 写 bpy 脚本，调 RoomKit 的函数。box 搭方块，cabinet 搭带门和抽屉的柜子，place_asset 从资产库（108 项）放现成模型。每个物体是一个带 instance_id 的根节点。
  4. 检查（Verify）。先导出几何，再把模型轮廓画回原视频帧（叠加图）。可选的 source_fit 拿剪影和 SAM 3 掩码比 IoU，低于 0.65 或边界偏差超过 12 px 就提醒。物理检查看穿透、悬空和 2 秒掉落。对不上就回第 3 步。
  5. 审查（Gate）。调 codex exec --image，另开一个只读的 Codex 会话。审查员按 JSON 格式逐个物体写观察，结论只有 accepted 或 rejected，rejected 就回去改。
  6. 交付。通过以后得到 .blend。每个物体能单独挪，柜门抽屉能开合，可以直接放进仿真器。博客后面还有人体动作、机器人动作和外观美化，我们都不用。
观察和测量的细节（代码里核实过）
  • 抽帧。默认 32 帧，可选 64，均匀抽取，一定包含首帧和尾帧。
  • 分辨率。每帧整体缩放到不超过 255,000 像素，宽高都取 14 的倍数。4:3 的画面约 574×434。
  • SAM 3。只按 person、glass、mirror、floor、wall 五个词分割，阈值 0.3，同类的所有实例并成一块。
  • 摆正。RANSAC 拟合以后，地面法向对齐 +Z、地面高度为 0、主墙对齐 X 轴。另外渲 3 到 5 张原视角参考图。
  • 测量端点。置信度低于 0.5，或者 3×3 像素块在 3D 里跨度超过 0.12 m，这个点被拒。
  • 面测量。measure_mesh 在帧上圈一个多边形，对 TSDF 表面拟合平面，支撑点少于 20 个就拒绝。
检查和审查的细节（代码里核实过）
  • 两种叠加图。quick_check 用光线求交，画考虑遮挡的可见轮廓；完整版 X-Ray 不管遮挡，逐物体画剪影，还渲俯视、正视、侧视。
  • source_fit 的门槛。IoU 0.65、边界 12 px。这两个数是分诊用的经验值，没有校准过，代码注释原文是 triage heuristics, not calibrated。
  • 物理检查。穿进别的物体超过 5 mm 算碰撞；底部往下 2 cm 内没有支撑面算悬空；刚体模拟 60 fps 跑 2 秒，每个物体默认 1 kg、摩擦 0.5，一次最多 40 个。
  • 谁能进仿真。只有闭合、体积和凸包相差不超过 2% 的部件。椅子、书架这类凹形物体会被跳过，只记原因。
  • 审查。只读沙箱（--sandbox read-only），超时 600 秒，结论必须覆盖每个物体 ID。
  • 会话层。Codex 的 Stop hook 在重建没完成时返回 decision: block，不让 agent 结束会话。
容易搞错
  • “米制”只是近似。cameras.json 的单位字段写明这是模型预测的米数、没有校准，原文是 predicted metres; uncalibrated。就算用一个已知长度做了尺度校正，measure.py 的输出里 physical_accuracy_validated 仍是 False。
  • SAM 3 在这里不分物体。观察阶段只分五类结构和人，每类的所有实例并成一块。物体级的 SAM 3 工具是可选的，共享流程不会自动调用。所以流程里没有自动的物体清单，要建哪些东西全凭 agent 看帧决定。
  • 审查和 Codex 绑死。审查员写死成 codex exec --image，Stop hook 的配置文件 .codex/hooks.json 没有随仓库发布。换别的驱动要自己补（见 第 9 章）。

2.2 agent 的一轮循环里到底发生什么

上一节的第 2 到第 4 步不是各跑一次。agent 会反复转圈：量一点、搭一点、看一眼、改一点。

下面这张时序图把一圈拆成七个动作。左边是 agent 在想什么，中间箭头是它交给工具的东西，右边是落到磁盘上的文件。

一圈循环：看帧 → 量 → 写 → 导出 → 叠图 → 读数 → 改
  1. 看帧。agent 打开观察阶段生成的参考视角图，决定这一圈处理哪几个物体。量尺寸和画叠加图都在 Pi3X 那 32 帧上做（约 574×434）；agent 一开始也会看原视频。
  2. 量尺寸。在某帧上挑两个像素点，写成 spec 文件交给 measure.py，读回米数（虚线箭头）。比如桌面左前角和右前角，量出桌宽。
  3. 写 bpy 脚本。按量出来的数调 RoomKit 的 box、cabinet、place_asset，Blender 在后台跑脚本，存成 .blend。
  4. 导出几何。blender -b 后台跑 export_model.py，得到所有三角面和“每个面属于哪个物体”。
  5. 画叠加图。quick_check 用光线求交，把模型的可见轮廓画回视频帧。叠加图回到 agent 手里，它自己看图找错位。
  6. 读数字。可选的 source_fit 给每个物体的掩码 IoU 和边界偏差；check-placement 把穿透、悬空、不稳写进 report.json，agent 要自己去读。
  7. 决定怎么改。agent 判断问题出在尺寸、位置还是朝向，改脚本，回到第 3 步，再从同一个视角重看。转到它觉得够好，再交给审查员。

第 2 步的 spec 文件长下面这样。字段名照代码，坐标和结果是编的，只为演示。

{"landmarks": [
   {"id": "L1", "label": "桌面左前角", "source_frame": 12, "pixel_uv": [212, 301]},
   {"id": "L2", "label": "桌面右前角", "source_frame": 12, "pixel_uv": [398, 296]}],
 "measurements": [
   {"id": "M1", "label": "桌宽", "kind": "horizontal_distance", "points": ["L1", "L2"]}]}
→ measurements.json 里多一行：M1 = 1.38 m（演示数字）
验证一共四层
  1. 数值检查。测量工具拒绝不可靠的端点；source_fit 给 IoU 和边界距离；物理检查给穿透、悬空、不稳三类问题。
  2. 图像检查。叠加图和 X-Ray 由 agent 自己看。
  3. 结构化审查。另一个只读会话逐个物体写观察，结论只有 accepted 或 rejected。
  4. 会话层。Stop hook 在重建没完成时不让 agent 收工。

几何准不准，除了可选的 source_fit 没有现成的数值指标，主要靠 agent 看图；物理检查的报告要 agent 自己去读。

容易搞错
  • agent 看图判断几何不一定靠谱。Agentic RSR（arXiv 2610.10479）v1 的消融里，去掉数值反馈后，通过视觉检查的场景从 18/18 掉到 6/18。那是别人的系统，但说明“只看图”有风险。
  • 检查用的帧就是建模时看过的帧。agent 对着同一批帧改到“看起来对”，不代表从别的角度也对。所以我们的评测用 CA-1M 的真值 3D 框，不用 AHa-3D 自己的检查分数（见 第 8 章）。

2.3 小物体在 AHa-3D 里怎么处理

从公开材料看，AHa-3D 对小物体的要求本来就放得很低。证据有四条，都在 10 月 14 日抓原文核对过。

  1. 对比实验的任务描述只要求近似。博客对比实验（Workflow ablation）交给两个 Astra agent 的要求是：墙和大家具要对上，小物体近似即可。原文是 They should match the walls and major furniture and approximate small objects. 注意这是那次对比实验的任务描述，不一定是发布版的默认提示词。
  2. 精度模式允许它随意。仓库 docs/LAYOUT_INSPECTION.md 定义了四档精度。“主要物体”（Major objects）档说桌面和柜顶的小摆件可以不准，除非用户点名，原文是 Small tabletop/cabinet-top decor may vary unless user-flagged。只有最严的 Precise 档才要求核对小物体。
  3. 审查员不拦。博客公开的审查样例里有一条不确定项，说小摆件、叶子形状、靠垫轮廓按范围只做近似，等级是不拦路（nonblocking）。原文是 Small decor, leaf shapes and individual cushion contours are approximate by scope。另一份逐项复核记录有 21 项，全是建筑构件、家具、灯和植物，没有杯子、书这类条目。
  4. 资产库里没有常见桌面物体。注册资产 108 项，小物体只有蜡烛、植物、瓷瓶、餐具、挂画、水龙头和台灯。杯子、书、显示器、键盘、遥控器都没有，“书”和“电视”只以材质名出现。博客图集说有 251 个物体资产，仓库只注册了 108 项。
生成模型这条路，作者试过又放下了

仓库 docs/OBJECT_GENERATION.md 第一段说，早先做过一次物体生成试点（SAM 3D Objects 和 TRELLIS.2），做完后搁置，生成适配器没有随这次发布。原文是 an earlier object-generation pilot (SAM 3D Objects and TRELLIS.2) was completed and then deferred; its generation adapters are not included in this release.

同一文件说生成网格适合复杂的静态家具和摆件，原文是 Generated meshes are candidates for complex static furniture and decor。未发布引用列表里的文件名显示，试点大约在 9 月 9 日。搁置原因没有公开。

博客的局限一节也承认，很小的物体和结构复杂的物体难以准确重建，原文是 very small objects and objects with complex structures remain difficult to reconstruct accurately。

容易搞错
  • 拿 A0 当小物体基线不公平。从公开材料看，AHa-3D 对小物体的要求本来就放得很低，A0 小物体差是意料之中。所以我们另设 A1“认真版”，提示词明确要求逐个建出看得见的小物体，作为公平基线（见 第 4 章）。
  • “加个生成模型”本身不是我们的贡献。作者自己试过，GRASE、LIVIN、GATOR 等也都做了。我们要回答的是这条被搁置的路线在整间房、同样预算下值不值。
  • 显示器不算小物体的例子。资产库里没有显示器是事实，但显示器多数落在 M 档（0.5–1.5 m）。讲小物体时用杯子、瓶子、书、遥控器、鼠标、台灯。
必记结论
  • AHa-3D 没有物体清单，小物体要靠 agent 自己看见。
  • 库里没有杯子和书，看见了也只能拿方块凑或者跳过。
  • 生成路线作者试过、搁置了，原因不明。我们量的就是它值不值。

2.5 我们保留什么、改什么

原则是尽量不碰 AHa-3D。它的工具、物理检查、审查门、可开合柜子在所有实验组里都原样保留，这样“和作者设置一样”这个前提才站得住。

我们只在“小物体怎么处理”这一点上加东西。设计文档把流程归成四个环节：找物体、建形状、摆准、检查，所有改动都落在这四个环节里。

灰色原样保留，彩色是各实验组加上去的
  1. 保留。AHa-3D 的五段、全部工具、物理检查、审查门、可开合柜子，所有组一模一样。A0 就是原版，作者的提示词原样运行。
  2. A1 改提示词。明确要求逐个建出所有看得见的小物体，只用代码和方块。这是公平基线，改的是“建形状”环节。
  3. A2 加清单。Boxer 在原始高清帧上检测，得到每个物体的 3D 框和 2D 裁剪图，作为待建清单交给 agent。agent 要逐项处理，或者说明为什么跳过。改的是“找物体”环节。
  4. A3 加生成和摆放。清单里的物体可以调 gen3d_request 生成网格，用 place_mesh 摆进场景，过了验收门才保留。A3r 按规则选（估计最长边小于 0.5 m 的生成），A3v 让 agent 逐个决定。
  5. A4 加精修。生成的物体被接受后，agent 再做 GATOR 式的“改、渲染、看”，每个物体最多 3 轮。只跑 5 个场景，是加分项。
  6. P0 另起一条流水线。完全不用大模型。Boxer 找框，每个框交给 SAM 3D 生成，place_mesh 自动摆，过不了验收就用框本身。它说明“按规则、不用大模型”这一端能做到多好。
另外几条对所有组都一样的规矩
  • 感知只算一次。每个场景的 Pi3X 和 SAM 3 结果在 Betty 上算好，所有组读同一份（第 3 章）。
  • 打补丁也要一样。10 月 26 日如果 AHa-3D 还不能无人值守跑完，就给 harness 打补丁，比如审查改用转发 shim、放宽 Stop hook。补丁对所有组一样（包括 A0），报告里称“打过补丁的 AHa-3D”。
  • 不允许人工干预。跑的过程中不能有人上手帮 agent 改。
必记结论
  • 灰色部分一律不动，所有组共享。
  • 每个实验组只比前一组多改一处：A1 改提示词，A2 加清单，A3 加生成，A4 加精修。
  • 各组的具体设计和场景数在 第 4 章，生成和摆放工具在 第 6 章。

3我们的系统架构

上一章是 AHa-3D 本身。这一章把它放进我们的整套系统里：什么在哪台机器上跑、文件怎么流、哪些东西所有实验组必须一样。

大白话

把整个项目想成一场厨艺比赛。

  • 备料只做一次。Betty 集群像中央厨房，把每个场景的“食材”（相机、点云、掩码、物体清单）一次备好，分装给所有参赛组。
  • 各组在同一个灶台上做。笔记本上的 AHa-3D 是灶台，同一把刀、同一口锅、同样的时限。
  • 评委只看成品。评测脚本拿真值（标准答案）打分，标准答案从头到尾不进厨房。

3.1 组件架构：两台机器之间只传文件

重活放在 Betty（学校的 GPU 集群，课程额度付费），要看图、要渲染的 agent 循环留在 Yifan 的笔记本上。两边之间只传文件。

Betty 的 B200 可以整卡用，也可以切成 MIG 切片用。MIG 是 NVIDIA 把一张大卡切成几块互相隔离的小卡；mig45 就是其中一块 45 GB 显存的切片，补贴价约是整卡的四分之一。

谁在哪跑，箭头上是传的文件
  1. Betty 上的感知。每个场景跑一次 Pi3X 和 SAM 3（作者默认的 32 帧、25.5 万像素），产出 bundle/。Boxer 在同样 32 帧的 1024×768 原图上检测，位姿和点图用 Pi3X 估的，产出 inventory.json。干净对照产出第二份清单 inventory_clean.json。
  2. AHa-3D harness。在笔记本上运行，原有工具和检查都不改，agent 由驱动模型扮演。主实验是 Codex CLI 加 GPT-6，开发和 5 个场景的复跑用 Claude Code 加 Opus 5.5。每次运行写一份 run_log.json。
  3. Blender。agent 写的 bpy 脚本在 Blender 5.2.1 后台运行，存成 scene.blend。Blender 只在笔记本上跑，因为 Betty 的 MIG 切片不支持图形接口。
  4. 我们写的工具。A3、A4 运行中由 agent 调 gen3d_request，把帧、掩码、点图交给 Betty 上的 SAM 3D，网格缓存到 gen/ 下（图里简写）。place_mesh 把网格配准进场景。细节在 第 6 章。
  5. P0 流水线。不经过 agent，也不调大模型。它用 Boxer 清单和干净对照清单各跑一遍，对每个框调同一套工具生成、摆放，过不了验收就用方块。最后自己写 scene.blend 和 export/objects.json。
  6. 评测脚本。从 agent 组的 scene.blend 导出每个物体的世界坐标框，写进 export/objects.json；P0 那一组直接用它自己写的。然后和 CA-1M 真值对齐、匹配，判三种结局，画漏斗，写进 results/。两份清单在“检测到”那一关也要读。评测细节在 第 8 章。

3.2 一个场景从头到尾

拿一个 CA-1M 场景走一遍。关键是第 2 步只做一次，第 3 步才按实验组分叉。

一个场景的七步：数据 → 感知 → 分叉 → 运行 → 生成 → 导出 → 评测
  1. 数据（Yujing）。把 CA-1M 的帧按 10 fps 合成 mp4 交给 AHa-3D，不下原始 .mov。22 个视频用固定种子分成 5 个开发、15 个测试、2 个备用，10 月 20 日前写进 configs/splits.json，之后不改。
  2. 感知（Mingjian，Betty）。Pi3X、SAM 3、Boxer、干净对照，每个场景只算一次，结果打包拷回笔记本。
  3. 分叉。七个实验组都读第 2 步的同一份结果，感知的随机性因此不会混进组间差异。P0 不调大模型，绕过第 4 步，直接进第 5 步。
  4. agent 运行（Yifan，笔记本）。每组每场景一次运行。所有组同一个墙钟上限、同一个轮数上限；跑崩或撞上限就重跑一次，还不行就拿最后存下的 .blend 打分，记为失败。
  5. 生成与摆放（Mingjian 的工具）。A3、A4 运行中由 agent 调用，P0 对每个框自动调用。生成在 Betty 上，配准在笔记本上，过不了验收门就退回方块。
  6. 导出（Yujing）。用 AHa-3D 的 export_model.py 按 instance_id 分组，导出每个语义根节点的世界坐标有向框，写进 export/objects.json。P0 直接写这个文件，不用导出。
  7. 评测（Yujing）。只用相机轨迹做 Sim(3) 对齐，匈牙利一对一匹配，每个真值物体判成“建好了 / 建坏了 / 漏了”，画漏斗，按场景 bootstrap 出置信区间。CA-1M 的真值只在这一步出现。
生成为什么不在 agent 的循环里卡住（按我们的理解）

gen3d_request 按“帧、掩码、后端、种子”缓存结果。P0 本来就要对每个 Boxer 框生成一遍，所以 A3 组请求同一个物体时，有可能直接命中缓存，不必等 Betty 排队。

能不能命中，取决于 A3 选的帧和掩码是否和 P0 一样。这一点设计文档没写，留给 Mingjian 实现时定。

设计文档也还没写两条和缓存有关的记账规则，我们建议这样定。

  • 命中缓存时，成本仍按一次生成记账。不然排在 P0 后面跑的生成组白占便宜，成本轴就不公平了。
  • 墙钟上限扣不扣等待生成的时间，和运行上限一起定。不管怎么定，所有生成组用同一条规则。

“高清帧”到底是什么
  • 帧。就是 Pi3X 用的那 32 帧，只是换成 CA-1M 的 1024×768 原图，没有多加帧。
  • 位姿。用 Pi3X 估的，不用 ARKit 的。
  • 深度。把 Pi3X 的点图放大到原图尺寸。SAM 3D 要的 pointmap 也从这里来。
  • 谁用。A2 起的 Boxer 检测和 A3 起的生成裁剪。高清帧消融就是把 A3v 换回 Pi3X 降采样后的帧，在 5 个场景上重跑。
估算 · 换成高清帧，小物体多出几个像素

算法：两种分辨率的边长比，按 1024 / 574 和 768 / 434 算。

  • 横向放大 1024 / 574 = 1.78 倍，纵向 768 / 434 = 1.77 倍，面积放大约 3.16 倍。
  • 一个在 Pi3X 帧里宽 20 像素的杯子，高清帧里约 20 × 1.78 = 36 像素宽。
  • 一块 100 像素的掩码，高清帧里约 100 × 3.16 = 316 像素。生成工具的门槛是约 200 像素（第 6 章），换帧前过不了，换帧后能过。

帧数没变，所以漏斗“看得见”这一关用的帧集合不变，只是多算一个分辨率。

容易搞错
  • Boxer 是“同源”的。Boxer 训练时用过 CA-1M 的训练集，在 CA-1M 上测会偏乐观。所以每张表都标“同源”，并放干净对照（SAM 3 掩码加 Pi3X 点云拟合框）。
  • 干净对照的范围有限。只在“检测到”这一关比较两种清单，P0 两种清单各跑一遍；agent 组只用 Boxer 清单，不重跑干净版。
  • 不能用被评测的物体做对齐。对齐只用相机轨迹，否则会把要测的误差抵消掉。
  • Pi3X 这一侧也可能沾了同源。它的前身 π³ 训练时用过 ARKitScenes（π³ 论文 §3.4），CA-1M 的视频就是 ARKitScenes；Pi3X 本身的训练集是否相同没核实。所以几何精度的绝对值可能偏乐观，报告里注明。所有组共用同一份感知结果，组间比较不受影响。

4七个实验组

这一章讲我们到底比什么。一共七个实验组：P0 和 A0 到 A4（A3 分成 A3r、A3v 两个）。它们跑在同一套流程上，每组只改其中一环。

大白话

把 agent 想成装修队的包工头：会看图纸，会叫师傅，自己也会动手。我们想知道它在"摆小东西"这件事上差在哪。

做法像试菜。同一口锅、同一份食材、同一个厨师，每次只换一样调料。味道变了，才能说是那样调料的功劳。

A0 到 A4 一组比一组多加一样东西。P0 干脆不请包工头，用一条自动流水线把东西摆上去，看看包工头到底值不值这份钱。

为了让"只改一环"成立，下面这些东西在所有组里完全一样（设计文档第 4 节）。

  • 同一份感知结果。每个场景的 Pi3X 和 SAM 3 结果只在 Betty 上算一次，按作者默认的 25.5 万像素、32 帧。所有组读同一份，感知的随机性就混不进组间差异。
  • 同一个软件版本。AHa-3D 提交 82f4b11（或我们 fork 后的固定提交），Blender 5.2.1。
  • 同一个驱动。同一个驱动模型、同一个推理强度，第 9 章细讲（算力、驱动和花费）。
  • 其余功能原样保留。可开合柜子、物理检查、审查门在所有组里都不动。

AHa-3D 的五个阶段怎么归成"找物体、建形状、摆准、检查"四个环节，见第 2、3 章（AHa-3D 是怎么工作的、我们的系统架构）。

4.3 A3r 和 A3v：谁来决定"生成还是搭"

A3r 和 A3v 共用同一条生成支路。两组唯一的区别是清单里每一项进来以后，由谁决定它走哪条路。

  • A3r 按规则。估计最长边小于 0.5 m（XS、S 两档）的走生成，其余照旧用代码搭。规则是设计文档第 15 节"我自己定的"第 1 条，用户可以否决。
  • A3v 大模型决定。agent 看这一项的裁剪图和测量值，逐个决定生成还是用代码搭。
生成支路里发生什么

gen3d_request 异步提交生成，按"帧、掩码、后端、种子"缓存结果。最好那一帧的掩码小于约 200 像素时，直接返回 too_small，这一项退回方块。

place_mesh 先用后端给的位姿或有向框做初始化，再做 ICP 和剪影坐标搜索，最后验收。验收要同时满足四条（设计文档第 6 节）。

  • 多帧平均剪影 IoU ≥ max(0.6, 方块版 IoU + 0.03)，也就是必须比方块好。
  • 观测点到网格的 Chamfer ≤ max(1.5 cm, 0.1 × 最长边)。
  • 尺寸在框的 0.75 到 1.25 倍之间。
  • 穿进支撑面不超过 1 cm。

这两个工具第 6 章细讲（生成与摆放工具）。

举个例子（按我们的理解）

清单里有一本书，估计最长边 0.3 m。A3r 的规则一看小于 0.5 m，就送去生成。A3v 的 agent 看了裁剪图，可能觉得书就是个长方块，直接用代码搭更省事。

反过来，一盆形状复杂的小植物，两组大概都会送去生成。到底哪种挑法更划算，正是 A3r 对 A3v 要量的东西。

容易搞错

规则用的是估计的最长边，来自清单里的 3D 框。评测分档用的是真值框的最长边（第 8 章）。两者可能不一致，一个真值 0.45 m 的物体可能被估成 0.55 m，于是 A3r 不会生成它。

4.5 每次运行的规则和削减顺序

"同样预算"在这个项目里有具体含义（设计文档第 15 节第 10 条）：所有组用同一个墙钟上限、同一个轮数上限，外加同一套失败处理规则。

大白话

像考试：所有人同一个时长、同一张答题卡。中途电脑死机可以重考一次；再死机，就按交上来的那份卷子判分，并记一笔"没考完"。

不能因为某组老死机就把它的卷子扔掉，那样会让爱死机的组看起来更好。

订阅额度可能不够跑完全部计划。设计文档预先定了削减顺序，额度不够时从上往下砍。

5漏斗：小物体丢在哪一关

漏斗是这个项目的主图（设计文档 9.5 节）。对每一个真值物体，我们记录它最远走到了哪一关。每一关都会筛掉一些物体，画出来像一个越来越窄的漏斗。

大白话

把漏斗想成机场的几道安检。乘客（真值物体）要依次过：进航站楼、过安检、到登机口、坐对座位。

最后没坐上飞机的人，卡在哪道关原因完全不同。卡在航站楼门口，是根本没进来；卡在安检，是被拦下了；到了登机口没上，是自己耽误了。

漏斗图就是把"每道关拦下了多少人"画出来。哪道关拦得最多，改进就该花在哪里。

5.1 四道关

四道关依次是看得见、检测到、建出来、摆准了。点"下一步"一关一关看，每关下面写着物体在这里丢掉的常见原因。

漏斗：一个真值物体最远走到哪一关
  1. ① 看得见。在该组实际用到的帧里（都是 Pi3X 那 32 帧），用 CA-1M 的激光深度判断遮挡，至少有一帧里可见面积 ≥ 100 像素（约 10×10）。A0、A1 按 574×434 算；P0、A2、A3、A4 在原图上找物体，按 1024×768 算。
  2. ② 检测到。清单里有一个框在宽松门槛内匹配上它。只有带清单的组有这一关（P0、A2、A3、A4）；A0、A1 没有清单，直接跳到第 ③ 关。
  3. ③ 建出来。最终场景里有物体在宽松门槛内匹配上它。A0、A1 没有第 ② 关，从 ① 直接到这里（上方虚线）。宽松门槛是 d̂ ≤ 1.0 或 IoU3D ≥ 0.1（第 8 章）。
  4. ④ 摆准了。通过严格判据。判据 I 和判据 D 分开各报一张表（第 8 章）。过了第 ③ 关却没过这一关的，就是"建坏了"。
  5. 天花板。第 ① 关只看几何，不调大模型就能算。它的高度就是这一组"不管 agent 多聪明都过不去的上限"，后面几关只会更低。A0、A1 的天花板按流程分辨率算，P0 和 A2 起按高清帧算。
"看得见"具体怎么算（按我们的理解）

对每个真值框、每一帧，把框投到这一帧上，再用 CA-1M 的激光渲染深度（512×384）判断哪些像素被前面的东西挡住，数剩下的像素。

帧集合固定是 Pi3X 抽的那 32 帧，分辨率按该组实际用的算：A0、A1 是 574×434，P0、A2、A3、A4 是 1024×768。任何一帧数到 ≥ 100 像素，这个物体就算看得见。

这一步只用真值数据，不碰 agent，所以用同一种分辨率的组结果完全一样。具体的投影和缩放细节由写评测脚本的人在开发集上定。

容易搞错
  • 漏斗记的是"最远走到哪一关"。一个物体过了 ③ 没过 ④，它的记录是"最远到 ③"。每关的高度是累计过关的物体数，后一关只会更矮。
  • A0、A1 没有第 ② 关。它们没有清单，物体从 ① 直接到 ③。比较 A1 和 A2 时，看第 ③ 关的高度。
  • 天花板不是一样高。每组按自己用到的帧算第 ① 关：A0、A1 按 574×434，P0 和 A2 起按 1024×768 原图，所以后者的天花板更高。漏斗图另画一条"流程分辨率下看得见"的参考线，两者之差就是高清帧带来的空间（设计文档 9.5 节）。

5.2 小物体在画面里占几个像素

第 ① 关为什么要紧，算一算就明白。一个物体在画面里占多少像素，取决于三件事：它多大、离相机多远、画面分辨率多高。

把这三个式子做成下面的计算器。拖动滑块，看同一个物体在三种分辨率下各占多少像素、能不能过关。

  • 574×434：AHa-3D 实际用的分辨率。Pi3X 把每帧缩到 25.5 万像素以内，宽高取 14 的倍数，1024×768 的帧就变成这个尺寸。A0、A1 的"看得见"按它算；高清帧消融也在这个尺寸上生成。
  • 1024×768：CA-1M 的原帧，也就是我们的"高清帧"。P0 和 A2 起在它上面找物体和裁剪，A3 在它上面生成。
  • 1920×1440：ARKitScenes 原始视频，我们不下载，放在这里作对照。
手算 · 默认值（10 cm、2 m、60°）

tan(60° ÷ 2) = tan 30° ≈ 0.5774。物体大小 0.10 m，距离 2 m。

  • 574 宽：f = 287 ÷ 0.5774 ≈ 497.1 像素；跨度 = 497.1 × 0.10 ÷ 2 ≈ 24.9 像素；面积 ≈ 24.9² ≈ 618 像素²。
  • 1024 宽：f = 512 ÷ 0.5774 ≈ 886.8；跨度 ≈ 44.3；面积 ≈ 1,966。
  • 1920 宽：f = 960 ÷ 0.5774 ≈ 1,662.8；跨度 ≈ 83.1；面积 ≈ 6,912。

三行都过了 200，默认值下都"可以送去生成"。把距离拉远，看 10 cm 的物体在多远处跌破两道门槛。

  • 574 宽：面积跌破 200（跨度 < √200 ≈ 14.1）在 497.1 × 0.10 ÷ 14.14 ≈ 3.52 m；跌破 100（跨度 < 10）在 497.1 × 0.10 ÷ 10 ≈ 4.97 m。
  • 1024 宽：886.8 × 0.10 ÷ 14.14 ≈ 6.27 m；886.8 × 0.10 ÷ 10 ≈ 8.87 m。
  • 5 cm 的物体，所有距离都减半，比如 574 宽时约 1.76 m 和 2.49 m。

两道门槛各对应哪一行：

  • too_small（200）：A3 在 1024 宽上生成，10 cm 的物体 6.27 m 外才 too_small。574 宽的 3.52 m 只在高清帧消融里遇到。
  • 看得见（100）：A0、A1 按 574 宽，4.97 m 外就过不了；P0 和 A2 起按 1024 宽，是 8.87 m。

574×434 怎么来的：1024×768 有 786,432 像素，缩放比例 √(255,000 ÷ 786,432) ≈ 0.569，得到约 583×437。

宽高往下取 14 的倍数，就是 574×434（41 × 31 = 1,271 个 patch）。取整方式是按我们的理解，以 Pi3X 代码为准。

容易搞错
  • 这是最好情况。面积按正对相机的正方形算。杯子是瘦高的圆柱，侧面还会被挡住一部分，真实可见面积通常更小。
  • 60° 是估计值。它是 iPad 主摄量级的猜测，没有按 CA-1M 的内参核对。视角越大，f 越小，物体占的像素越少。
  • 两道门槛来源不同。100 像素是"看得见"的门槛（设计文档 9.5 节）；200 像素是 gen3d_request 返回 too_small 的门槛（设计文档第 6 节）。两个都是我们定的初值。

默认值下，10 cm 的杯子在 2 m 外，在 AHa-3D 的分辨率里只有约 25 像素宽。这就是 A2、A3 坚持在高清帧上找物体和裁剪的原因。

5.3 报告主图长什么样

报告的主图是一组堆叠条形：每个实验组、每个尺寸档各画一根。下面这张是示意，条的长度是随手画的，不代表我们预期的结果。

读这张图分三步。

  1. 先看灰色和红线。灰色是第 ① 关就丢的，任何组都救不回来。A0、A1 的灰色从红线开始；P0 和 A2 起按高清帧算，越过红线的那截就是高清帧带来的空间。

5.4 怎么读漏斗：三种典型形状

漏斗最有用的地方，是告诉我们下一步该往哪里使劲。下面三种形状对应三种不同的结论。每个小图最左是全部真值物体，往右依次是过了 ①②③④ 的数量，红色虚线框是丢得最多的地方。

情形漏斗长什么样说明什么往哪使劲
一：卡在 ① 看得见大部分小物体在该组用到的 32 帧里根本没有 100 像素瓶颈在上游，agent 再聪明也救不回来。设计文档第 13 节把这种结果也算作一个发现更多帧、更高分辨率、拍得更近；高清帧消融（第 4 章）给出具体数字
二：卡在 ② 检测到看得见很多，但没被清单框到检测器在第 ② 关丢得多，找物体是瓶颈换更好的检测器，或对照干净清单看是不是 Boxer 的问题；也可以做 Boxer 微调（第 14 章）
三：卡在 ③ 或 ④找到了却没建，或建歪了agent 或生成的问题生成路由（A3r 对 A3v）、place_mesh 的配准和验收、精修（A4）值不值
必记
  • 四关依次是看得见、检测到、建出来、摆准了；每个真值物体记"最远到哪一关"。
  • 看得见不调大模型，是每组的天花板：A0、A1 按流程分辨率算，P0 和 A2 起按高清帧算。
  • 只有带清单的组（P0、A2、A3、A4）有"检测到"这一关。
  • 漏斗的用处是指路：丢在哪一关，就往哪一关使劲。

6生成与摆放工具

A3、A4 和 P0 要把小物体从“一个方块”换成“一个生成出来的网格”。这件事分两半：先生成形状，再把形状摆到房间里正确的位置。

我们为此写两个工具，gen3d_request 和 place_mesh。负责人是 Mingjian：先在笔记本上用 Hunyuan3D-2mini 写通、调好，正式实验换成 Betty 上的 SAM 3D。

大白话

像网购一件小家具。gen3d_request 是下单：照着照片订一件长得像的，订完不用守在门口等。place_mesh 是安装：把到货的家具对着照片挪到原位，挪完请人验收。

验收标准很硬：装上去必须比原来那个纸箱占位（方块）更像照片，不然就退货，继续用纸箱。

6.1 为什么拆成两个工具

理由有两条，都来自调研笔记 02 的接口建议。

  1. 生成慢，不能让 agent 干等。生成走异步批处理：agent 一次提交好几个物体，生成期间接着用方块搭别的东西。
  2. 摆错了只重摆，不重生成。比如瓶子被摆成横躺，只要换个朝上轴重跑 place_mesh（估计几秒到几十秒），不用再花一次生成。
估算 · 一个物体要多久（调研笔记 02 第 7.3 节，多数是推算）
  • SAM 3D 自己部署：A100 上 13.0 ± 1.4 秒一个，不含加载模型（RecGen 论文表 S3 实测）。
  • 配准加剪影精修：约 5 到 30 秒（推算）。
  • 每个候选合计约 30 到 90 秒（推算）。
  • 一个场景 15 个物体、每个 2 个候选：串行约 15 到 45 分钟，异步并发能缩到约 5 到 10 分钟（推算）。

B200 上的速度没有测过，第 1 周在 Betty 上跑通后用实测数替换。

调研笔记 02 第 0 节第 8 条、第 7.2 和 7.3 节；设计文档第 6 节。

6.2 gen3d_request：从清单里的一个物体到一个干净的网格

接口照抄调研笔记 02 的 §7.2，只留我们会用到的后端。

gen3d_request(
  object_ids,              # 清单里的物体 ID（A3、A4 来自 Boxer 清单）
  backend = "sam3d",       # 正式实验；开发期用 "hy3d_shape"
  n_candidates = 2,        # 每个物体几个候选，上限 3
  frames = "auto",         # 自动挑帧
  inpaint = "auto",        # 估计遮挡超过约 30% 才补全
  texture = False          # 先只要形状，接受以后再补纹理
) → job_id                 # 异步：先拿号，之后再取结果
gen3d_request 内部六步
  1. 挑帧，先过门槛。按“掩码面积 × 不贴图像边的比例 × 清晰度”给帧排序，取前几帧。最好那一帧的掩码不到约 200 像素（约 14×14）就返回 too_small，用方块。A3 起用 1024×768 的高清帧。
  2. 裁 RGBA。用 SAM 3 的掩码当透明通道（alpha），四周留 10% 到 20% 的边。不让通用去背景模型在几十个像素上自己猜轮廓。
  3. 可选补全。估计遮挡超过约 30% 时，先用图像编辑模型把被挡住的部分补出来。原图也保留，作为另一个候选一起参加后面的打分。
  4. 调后端。正式实验用 Betty 上的 SAM 3D，开发期用笔记本上的 Hunyuan3D-2mini。每个物体默认 2 个候选（换帧或换种子），上限 3 个。
  5. 清理网格。只留最大的连通块（生成结果常带碎片），减面到不超过 2 万个三角面，统一成 Z 朝上、以米为单位。
  6. 缓存。按（帧、掩码哈希、后端、种子）存盘，同样的请求第二次直接返回。提交时拿到的 job_id 用来取结果，place_mesh 从这里取网格。
算例 · 生成器实际看到多少像素（调研笔记 02 第 4.1 节，推算）

生成器内部都会把物体裁剪放大到固定尺寸。拿 Pi3X 帧（574×434）里一个 60×60 像素的杯子来算。

  • SAM 3D：物体那一路放大到 518。518 ÷ 60 ≈ 8.6，加上留边约 8 倍。
  • TRELLIS.2：放大到 1024，裁剪不留边，1024 ÷ 60 ≈ 17 倍。

放大不会凭空增加细节，模型拿到的信息还是那 60 像素。所以 A3 起要用高清帧，同一个杯子在 1024×768 的原图里宽约 60 × 1.78 ≈ 107 像素。

容易搞错
  • SAM 3D 吃的是整张图加掩码。它自己在掩码周围留边、缩放到 518，没有去背景模型，直接用“图像 × 掩码”，所以掩码好坏直接决定结果。第 2 步的 RGBA 裁剪主要是给 Hunyuan 用的。
  • Hunyuan 必须自己给 alpha。没有 alpha 时，整张图都会被当成物体。
  • “清晰度”这一项没有论文依据。用 Laplacian 方差衡量清晰度是我们自己的选择，开发集上看效果再定。
  • 别每帧各生成一个。AHa-3D 的文档提醒，不要每帧各生成一次、再假设它们彼此一致，原文是 Do not regenerate each video frame and assume its meshes are temporally consistent。

调研笔记 02 第 4.1、4.3、4.5、7.2 节；设计文档第 6 节（too_small 门槛、缓存键）。

6.3 place_mesh：把网格摆准

拿到网格以后，要定它在房间里的位置、朝向和大小。做法照 φ-RIE、ReScene、GRASE 三篇论文的配方拼起来。

place_mesh(object_id, candidate_id,
           init = "backend_pose" | "obb",   # SAM 3D 用后端给的位姿；Hunyuan 用 3D 框
           dof = 7 | 9,                     # 9 = 三个轴各自缩放
           support = 支撑面 ID 或 None,       # 比如桌面
           yaw_hint = 偏航角提示 或 None)
→ PlacementResult（JSON）

几个词先解释一下。

  • OBB（有向包围盒）。能转的 3D 框，由中心、三边长和朝向定义。
  • ICP（迭代最近点）。反复“给每个点找最近的对应点、再算一个最好的变换”，把一组点贴到另一组点上。
  • 剪影 IoU。把网格按某个相机投影到图上得到剪影，和 SAM 3 掩码算交集除以并集。1 是完全重合。
  • Chamfer 距离。这里指单向的，观测到的每个点到网格表面的平均距离，越小越贴。
place_mesh 四步走到验收门
  1. 初始化。SAM 3D 输出自带相机坐标系下的旋转、平移、尺度，用 Pi3X 的相机位姿换到世界系就是起点。Hunyuan 的网格没有位姿，尺度取点云的稳健 OBB，偏航每 10° 一个起点，再加 5 个候选朝上轴。图里红点是观测到的点。
  2. ICP 贴点云。用观测到的部分点云去贴完整的网格，只算单向距离（观测点到网格），因为网格背面本来就没被拍到。尺度限制在 OBB 的 0.75 到 1.25 倍之间（GRASE 的范围），底面贴住支撑面（桌面）。
  3. 剪影搜索。取 3 到 5 帧，比较网格剪影（虚线）和 SAM 3 掩码（绿块），在有限范围内逐个坐标微调，分 3 层、每层 4 遍，步长 1、0.5、0.25。目标是“1 − 掩码 IoU”加边界距离、最差视角、点到面距离。
  4. 验收门。四个条件都过才算数，详见 6.4 节。图里的数是示例。剪影 IoU、Chamfer 取自调研笔记 02 的返回值样例，尺寸比和穿透深度是为演示编的。
  5. 结局。过了就是 accepted，网格和它的 4×4 世界变换（matrix_world）写进场景；不过就是 rejected_fit，这个物体用清单里的框本身（方块）。不管哪种，结果都写成一份 JSON 返回给调用者并记进日志。
看一份完整的返回值样例（调研笔记 02 第 7.2 节）

mesh_glb 在物体自己的坐标系里：Z 朝上、单位米、原点在底面中心。matrix_world 把它放进世界坐标系。

容易搞错
  • 剪影不必用可微渲染。在网格表面采 2 万个点，投到图上再膨胀一下就是剪影。这样能避开 nvdiffrast 在新显卡上的编译问题（推算）。
  • 小物体上点云不可靠。一个 60 像素的物体在 Pi3X 点云里可能只有几百个点，深度噪声相对物体尺寸很大（推算）。所以对小物体，剪影项比点云项更可靠，“底面贴支撑面”这条约束也很重要。
  • SAM 3D 的尺度是各向同性的。发布代码把三个轴的尺度取平均，扁的、长的物体会被缩成一样的比例。需要时用 dof = 9 让三个轴各自缩放。
  • fal 上的 SAM 3D 坐标约定没写明。返回的四元数、平移、尺度是什么坐标系，要拿已知物体实测。这正是 fal 那 10 美元的用途（第 9 章）。

6.4 验收门：四个条件，缺一不可

验收门决定一个生成网格能不能留在场景里。核心只有一句话：必须比方块好。

算例 · 三个物体过不过得了门

杯子（最长边 0.11 m）。方块版剪影 IoU 0.62，网格 0.71。

  • 剪影门槛 = max(0.6, 0.62 + 0.03) = 0.65，0.71 ≥ 0.65，过。
  • Chamfer 门槛 = max(1.5 cm, 0.1 × 11 cm) = max(1.5, 1.1) = 1.5 cm。实测 1.2 cm，过。

一本书。方块本来就很像书，方块版 IoU 0.70；网格 0.72。

  • 剪影门槛 = max(0.6, 0.70 + 0.03) = 0.73，0.72 < 0.73，不过，退回方块。生成虽然没变差，但也没好到值得换。

一个台灯（最长边 0.4 m）。

  • Chamfer 门槛 = max(1.5 cm, 0.1 × 40 cm) = 4 cm。物体越大，允许的绝对误差越大，保底是 1.5 cm。

以上数字是演示用的，杯子那组取自调研笔记 02 的返回值样例。

为什么非要有这道门。证据有三条。

  1. 直接接生成器可能更差。SEIG（arXiv 2606.02580）拿 Blender agent VIGA 做对照：完整版 VIGA 先用 SAM 和 SAM-3D 分割、生成每个物体；去掉这两个模型、只靠大模型搭的版本，在两个数据集上 CLIP 分数都更高，PSNR 一高一低（单张图片输入，见下表）。SEIG 的作者说完整版生成的网格碎、颜色错，拼不成协调的场景，还会被 agent 改写纹理，原文是 fragmented, mis-colored meshes that fail to assemble into a coherent scene。
  2. SAM 3D 自己也设门。它的布局后优化在掩码 IoU 低于 0.5、或者没超过初始 IoU 时拒绝结果。在 ADT 数据集上，1027 个实例里只有 554 个接受了优化。
  3. ReScene 也设门。配准后 RMSE 不能变大、内点率下降不超过 0.01，否则保留原位姿。

F1@0.01、FoundationPose、ADD-SB 是什么
  • F1@0.01。比形状的分数。把生成的形状和真值形状都撒成点，距离在 0.01 以内能找到对方的点算“对上”，再把查准率和查全率合成一个数。0 到 1，越高越像。
  • FoundationPose。NVIDIA 的物体位姿估计模型。给它一个现成的网格和带深度的图，它估出网格在相机里的旋转和平移。它不估尺度，网格必须已经是米制大小。
  • ADD-SB 误差。衡量位姿摆得准不准，单位米，越小越好。按我们的理解它和常用的 ADD-S 同类：把物体按预测位姿和真值位姿各摆一遍，量两份点之间的平均最近距离，所以杯子这类对称物体绕自己的轴转一下不会被算成错。

50 个物体的小对比就是为这个做的。它是物体级实验，不进 agent 循环，排在 11 月 10 日到 16 日。

6.6 失败了怎么办

生成这条路随时可能出岔子。原则只有一条：任何失败都有退路，退到底就是方块，并且每次决定都记日志。

失败情况处理
后端报错或超时重试 1 次，仍然失败就用方块。笔记建议换另一个后端重试（fal 和自部署互为备份），但我们的 fal 只有 10 美元、只用于核对，正式实验里具体怎么重试由 Mingjian 定
朝上轴错了（瓶子横躺之类）依次试 5 个候选的朝上轴（φ-RIE 的做法）
旋转对称的物体（杯子、花瓶）偏航定不下来只看剪影；偏航误差不计入失败
网格碎、颜色错（SEIG 在 VIGA 上观察到的问题）只留最大连通块；连通块太多直接拒绝；不许 agent 改写生成网格的材质
补全时多画了东西（多出个把手之类）原图那个候选一起打分，剪影 IoU 高的胜出
场景预算用完每个场景设生成次数上限（笔记建议例如 30 次）和美元上限，超了剩下的物体都用方块
每个决定记日志：后端、帧、门槛值、最后用的是方块还是网格，方便之后做“方块 vs 生成”的分析
必记结论
  • 两个工具拆开：生成异步，摆放可以单独重跑。
  • 验收门的核心是“必须比方块好”，四条全过才留。
  • SAM 3D 自带位姿，Hunyuan 要从零配准；50 个物体的小对比量这个差距。
  • 任何失败退到底都是方块，每个决定都进 run_log.json。

7.1 一个 CA-1M 场景里有什么

每个 CA-1M 视频是一个 tar 包（验证集中位数 0.51 GB）。里面的东西分两类：流程能看的，只有 RGB 帧；其余全部只给评测。

拆开一个 CA-1M 视频：每样东西去哪
  1. RGB 帧。1024×768 的 PNG，帧间隔 100 ms，约每秒 10 帧。CA-1M 已经把竖拍的帧转正，没有 .mov。这是流程唯一的输入：合成 input.mp4 交给 AHa-3D，高清帧也从这里取原图。
  2. RT.json 和 T_gravity.json。RT.json 是注册到激光坐标系的相机位姿，评测时拿它的相机中心做对齐（第 8 章）。T_gravity.json 是每帧的重力方向，按我们的理解用作对齐的重力约束。
  3. 激光渲染深度。FARO 激光扫描渲染出的深度图，512×384，比手机自带的深度准得多。漏斗第 ① 关"看得见"用它判断遮挡（第 5 章）。
  4. world.gt 框。每个视频约 125 个 3D 框，穷举、不分类别，在激光扫描坐标系里（z 朝上），带 3×3 旋转和 8 个角点。去掉结构件后存成 gt/boxes.json，只给评测。
  5. ARKit LiDAR 深度。256×192，手机自己测的。流程不用它，评测有更准的激光深度，也不用它。
容易搞错
  • 流程里的位姿和深度都来自 Pi3X。CA-1M 的 ARKit 位姿、激光深度、注册位姿一律不进入流程（设计文档第 8 节）。否则就成了"偷看答案"。
  • CA-1M 没有发布 mesh 和掩码。所以在 CA-1M 上只评"在不在、准不准"，不评形状。

7.5 输入视频怎么来，"高清帧"是什么

AHa-3D 要的是一段视频。我们用 CA-1M 的帧按 10 fps 合成 mp4（每个场景一个 input.mp4），原始 .mov 不下载（每个约 0.9 GB，硬盘只剩约 65 GB）。

输入视频和高清帧：同一批帧，两种分辨率
  1. 合成视频。把 CA-1M 的帧按原顺序拼成 10 fps 的 input.mp4。CA-1M 本来就是约 10 fps，所以一帧对一帧，不丢不补。
  2. Pi3X 抽帧。从整段视频里均匀抽 32 帧，必须包含首帧和尾帧；每帧缩到 25.5 万像素以内，宽高取 14 的倍数，也就是 574×434。
  3. 流程往下走。Pi3X 输出每帧的相机位姿和近似米制的点图，AHa-3D 后面的环节都用它。所有实验组共用这一份。
  4. 高清帧。就是 Pi3X 用的那 32 帧，换成 1024×768 的原图。帧号相同，只是分辨率高。
  5. 配上几何。位姿用 Pi3X 估的；深度用 Pi3X 的点图放大到原图尺寸，SAM 3D 要的 pointmap 也从这里来。
  6. 用在哪，以及不用什么。高清帧给 A2 起的 Boxer 清单和 SAM 3D 的裁剪用。CA-1M 的真值传感器数据一律不进流程，所以流程始终是"单目视频进来"。
必记
  • 高清帧 = Pi3X 那 32 帧的 1024×768 原图，位姿和深度都来自 Pi3X。
  • 漏斗"看得见"那一关的帧集合因此不变，只是多算一个分辨率。
  • 高清帧消融（A3v 改用降采样帧）只改分辨率，不改帧数。
容易搞错

"高清帧"不等于"更多帧"。帧号和 Pi3X 用的完全一样。只在 32 帧之间出现过的物体，高清帧也帮不上忙，它在漏斗第 ① 关照样会丢。

8评测

这一章讲怎么给一个重建好的场景打分（设计文档第 9 节）。核心问题只有一个：每个真值物体，最后建好了、建坏了，还是漏了。

大白话

评测像阅卷。考生交上来的 .blend 是一张画在透明纸上的答卷，标准答案是另一张透明纸。

先把两张纸叠对齐，再按大小把题目分组，一道真值题配一个答案，最后每道题判"对、半对、没答"。叠纸的时候只能对准纸的边框（相机轨迹），不能拿答案本身去对，否则错的也会被对成对的。

8.1 评测流水线

从 .blend 到最后的图表一共六步。每一步的输入输出都写在箭头上。

评测流水线：从 .blend 到漏斗和前沿
  1. 导出预测框。评测脚本用 AHa-3D 自带的 export_model.py，从最终的 .blend 里导出每个语义根节点（按 instance_id 分组）的世界坐标有向框，写成 export/objects.json。P0 不经过 .blend 导出，直接写这个文件。
  2. 对齐。Pi3X 的坐标系和 CA-1M 的不一样。把两边的相机中心对应起来，解一个 Sim(3)（尺度、旋转、平移），加重力约束；另报一个尺度固定为 1 的 SE(3) 版本。见 8.2 节。
  3. 去结构件、分档。墙、地面、天花板、门框这些结构件不算物体，先去掉。剩下的按真值框最长边分成 XS、S、M、L 四档，每档报真值物体的数量。见 8.3 节。
  4. 一对一配对。用匈牙利算法把预测和真值一对一配起来，不看类别（CA-1M 有 48% 的框只写 "object"）。代价是按大小归一化的中心距离 d̂。
  5. 三种结局。每个真值物体归为建好了、建坏了、漏了之一。两套严格判据 I 和 D 分开，各出一张表。见 8.4 节。
  6. 汇总。画漏斗（第 5 章），做组间配对比较、按场景 bootstrap 的 95% 区间，最后画成本-精度前沿。见 8.5 节。
匈牙利算法是什么

它解的是"一对一分配"问题：给一张代价表（行是真值，列是预测），找一种配法，让每个真值最多配一个预测、总代价最小。

贪心地"每个真值挑最近的"会出问题：两个挨着的杯子可能抢同一个预测，另一个预测却没人要。匈牙利算法一次性看全局，不会出现这种情况。

8.2 为什么只用相机轨迹对齐

重建出来的场景在 Pi3X 自己的坐标系里，和真值差一个整体的缩放、旋转、平移。打分前要先把它挪到真值坐标系里。

挪的依据只能是相机轨迹，绝不能用被评测的物体。这是设计文档列的反目标之一。

具体做法是 Umeyama 算法：把 Pi3X 估的每帧相机中心 pᵢ 和 CA-1M 注册过的同一帧相机中心 qᵢ 配成对，求一个尺度 s、旋转 R、平移 t，让下面这个和最小。

min over s, R, t :   Σᵢ ‖ qᵢ − (s·R·pᵢ + t) ‖²

pᵢ ：Pi3X 估的第 i 帧相机中心
qᵢ ：同一帧在 CA-1M RT.json 里的相机中心（激光坐标系）
s  ：尺度；SE(3) 版本固定 s = 1
R  ：旋转；加重力约束（按我们的理解：只绕竖直轴转）
t  ：平移

旋转不受限时，它有闭式解（用一次 SVD），不用迭代，相当于轨迹评测工具 evo 里的 --align --correct_scale。

加了重力约束、只许绕竖直轴转时，旋转只剩一个角度，不能直接套那一步 SVD。按我们的理解，要改成只在水平面上求这个角（用 atan2），尺度和平移再跟着算，仍然是闭式解。

为什么还要报一个不修尺度的版本

Pi3X 给的是"近似米制"的点云，尺度可能偏。Sim(3) 会把这个偏差修掉，SE(3) 不修，两个一比就看得出 Pi3X 自己的尺度误差。

尺度误差会推着物体一起偏。03 号笔记的估算：全局尺度差 10% 时，离对齐中心 3 m 的物体会偏约 30 cm，形状再完美也算不上摆准。

手算 · 尺度差 10% 推着物体走多远

对齐中心在原点，一个物体的真实位置离原点 3 m。重建的尺度大了 10%，它就被放在 3 × 1.1 = 3.3 m 处。

偏差 = 3.3 − 3 = 0.3 m = 30 cm。对 8 cm 的杯子来说，这已经远远超出宽松门槛（见 8.4 节，d̂ ≤ 1 大约是 7 cm）。

容易搞错
  • VSI 开发集和 BVB 重新打分没有相机轨迹。只能退而用 L 档家具加地面来对齐，所以 L 档自己不打分，只给 XS、S、M 三档打分，表里注明。
  • 帧对应是现成的。输入 mp4 就是用 CA-1M 的帧合成的，Pi3X 抽到的每一帧都能找到对应的 CA-1M 帧（按我们的理解）。RT.json 只覆盖注册过的帧，没注册的帧不参与对齐。

这种"用轨迹对齐、再评物体"的做法有先例。SpatialLM 附录 C.3 先把 SLAM 估的相机轨迹对齐到真值轨迹，再评检测。

原文是 we align the estimated camera trajectory from MASt3R-SLAM to the ground-truth camera trajectory。

8.4 三种结局

配对之后，每个真值物体都要归进三种结局之一。判断顺序是一棵小决策树，点"下一步"一层一层看。

一个真值物体的三种结局
  1. 配上了吗。匈牙利算法给每个真值物体最多配一个预测，代价是 d̂ = ‖c_pred − c_gt‖ / r_gt，r_gt 是真值框的半对角线长。
  2. 严格判据。两套分开报。判据 I：IoU3D ≥ 0.25（另报 0.5），方便和前人比较。判据 D：d̂ ≤ 0.5，并且最长边之比在 0.67 到 1.5 之间。通过就是"建好了"。
  3. 宽松门槛。没过严格判据，但 d̂ ≤ 1.0 或 IoU3D ≥ 0.1，就是"建坏了"：东西建了，位置或尺寸不对。
  4. 漏了。根本没配上，或者配上了但连宽松门槛都没进。

为什么要两套判据？IoU 对小物体非常敏感，一点偏移就掉很多，而 d̂ 按物体大小归一化，大小物体一视同仁。3D-MOOD 也指出 IoU 对小物体和薄物体太苛刻，原文是 too restrictive。

手算 · 8 cm 的杯子偏 3 cm

假设：杯子当成边长 8 cm 的立方体；预测框和真值框一样大、都和坐标轴对齐；预测只沿一个轴偏了 3 cm。

  • IoU3D：重叠部分是 5 × 8 × 8 = 320 cm³；两个框各 512 cm³，并集 = 512 + 512 − 320 = 704 cm³。IoU = 320 ÷ 704 ≈ 0.455，从 1 掉了一半多。
  • d̂：半对角线 r = √3 × 8 ÷ 2 ≈ 6.93 cm。d̂ = 3 ÷ 6.93 ≈ 0.433。
  • 结论：0.455 ≥ 0.25，过判据 I；0.433 ≤ 0.5 且边长比为 1，过判据 D。两套都算"建好了"。

同样偏 3 cm，换成边长 2 m 的立方体：IoU = 197 ÷ 203 ≈ 0.970，d̂ ≈ 0.017。对大家具，3 cm 几乎没影响。

反过来算门槛。沿一个轴偏 x cm 时 IoU = (8 − x) ÷ (8 + x)，d̂ = x ÷ 6.93。

  • IoU 降到 0.25：x = 4.8 cm。
  • d̂ 到 0.5：x ≈ 3.46 cm。
  • d̂ 到 1.0：x ≈ 6.93 cm。这就是宽松门槛的边，因为 IoU ≥ 0.1 只撑到 x ≤ 6.55 cm，两者取"或"以宽的为准。
容易搞错
  • IoU 还看偏的方向，d̂ 不看。同样偏 3 cm，如果沿体对角线偏（三个轴各偏约 1.73 cm），IoU 只有约 0.317，d̂ 仍是 0.433。
  • 阈值都是我们定的初值。0.25、0.5、0.67–1.5、1.0、0.1 定死之前还没有任何 agent 运行，所以只在开发集上做两项合理性检查（设计文档 9.4 节）。
    • 真值对真值：应该全部"建好了"。
    • 检测器直接输出的框（Boxer 和干净对照）对真值：看分布合不合理。
    不拿任何 agent 组的输出来调阈值。10/20 前写进 configs/thresholds.json，之后不改。
  • IoU3D 的计算：03 号笔记建议用 pytorch3d.ops.box3d_overlap，输入是 8 个角点，顺序有规定，写脚本时要按文档排。

8.5 统计和成本

有了每个物体的结局，最后一步是比较各组，并且把钱算进去。设计文档 9.6、9.7 节定了四件事。

  • 配对比较。同一个真值物体在不同组里的结局两两对照，不只比总数。
  • 按场景 bootstrap。把 15 个测试场景有放回地重抽很多次，每次算一遍组间差，取中间 95% 作为置信区间。
  • 噪声底线。A1 和 A3v 在 5 个场景上各跑第二次，量出"同一组跑两次差多少"。组间差距比它小的，不下结论。
  • 成本。每次运行记 token 数（输入、缓存、输出）、按 API 价折算的美元、墙钟时间、fal 费用。
大白话

为什么按场景重抽，不按物体？同一个房间里的物体不是互相独立的：光线差、视频晃，整个房间的物体一起遭殃。按场景抽，才能把"碰巧抽到几个好拍的房间"这种运气算进区间里。

最后的结论写成成本-精度的帕累托前沿，不评"哪种最好"。横轴是每个场景花的钱，纵轴是小物体召回。

必记
  • 对齐只用相机轨迹（Sim(3) 加不修尺度的 SE(3)），绝不用被评测的物体。
  • 分档按真值框最长边：XS < 0.2、S 0.2–0.5、M 0.5–1.5、L ≥ 1.5 m。
  • 每个真值物体归为建好了、建坏了、漏了；判据 I 和 D 各报一张表。
  • 组间差要越过"同组跑两次"的噪声底线才下结论；结论写成成本-精度前沿。
  • 精确率（多建出来、对不上真值的物体）作次要指标。CA-1M 是穷举标注，这个数有意义。
  • 所有阈值 10/20 前写进 configs/thresholds.json 定死。

订阅不按次计费，所以成本轴要靠自己记 token 日志再按官方 API 价换算；价格和额度见第 9 章。

9.2 驱动模型怎么选，为什么全程不换

驱动模型就是扮演 agent 的那个大模型。AHa-3D 的 harness（工具和流程）不变，换的只是“谁在想”。

为什么主实验用 GPT-6。Codex 是 AHa-3D 原生的驱动方式，作者博客用的就是 GPT-6 Astra（推理强度 medium）。这样最接近复现作者的设置。

为什么还要 Claude。开发调试用得多，Claude Max 的额度可以分担；5 个场景的复跑回答“换一家模型，结论还成立吗”。

公开证据能参考的是 Agentic RSR（arXiv 2610.10479），它在 18 个 Blender 场景上比过一批模型。

为什么全程不换驱动
  • 组间比较要求同一个驱动。A1 和 A3v 之间的差，必须只来自“加没加生成”，不能混进“换了个模型”。
  • 削减顺序里没有“换驱动”这一项。额度不够时砍场景、砍组、砍重复，驱动不换。换驱动会破坏“复现作者设置”这个前提。
  • 推理强度也固定。设计文档要求所有组同一个推理强度，具体档位没写死；作者博客用的是 medium。
  • Claude 复跑是另一张表。它和主实验分开报，不混进同一个比较。

  • 便宜模型在长任务上可能撑不住。Haiku 5.5 跑 office48 只用了 5.7 分钟、67 轮，结果粗糙，验收在第一关没过；它在 BVB 榜上分数却不差。BVB 是几分钟的短任务，榜单分数不能直接搬。

9.4 成本口径和运行次数

订阅按月付费，这个数并不是我们真花出去的钱。它只用来在各组之间、各模型之间做同一把尺子的比较。

9.5 硬盘和存储

笔记本硬盘只剩约 65 GB，这条约束直接决定了“什么数据不下”。

  • 不下原始 .mov。ARKitScenes 的原始视频每个约 0.9 GB，22 个约 20 GB。我们用 CA-1M 的帧按 10 fps 合成 mp4，就不需要它。
  • 大文件放 Betty。模型权重和中间结果都放 Betty；笔记本只放评测数据和最终的 .blend。
  • inode 可能比容量先用完。inode 是“文件个数”的配额，Betty 的 home 是 50 GB、25 万个。AHa-3D 每次运行会生成大量帧和中间文件，所以作业时写到节点本地的 /tmp/$USER，结束后打成 tar 包拷回。
  • 节点本地盘要自己清。/tmp/$USER 约 500 GB，同一节点上的人共用，用完要拷走并删除。
容易搞错
  • bundle 还是要拷回笔记本。agent 的测量和叠图工具在笔记本上读 bundle/。单个 bundle 多大，第一个场景跑完就量，再看 20 个场景放不放得下（设计文档没算这一笔，按我们的理解要预留）。
  • ScanNet++ 不是一定会下。要教授手签，11 月 2 日前批下来才加 5 个场景做形状指标。
必记结论
  • 订阅只驱动 agent；3D 模型在 Betty 和笔记本上跑；fal 只花 10 美元做核对。
  • 主实验 Codex 加 GPT-6，Claude 加 Opus 5.5 做开发和复跑，全程不换驱动。
  • 第 1 周先量额度，再定墙钟和轮数上限。
  • 成本轴是 API 等价美元，每次运行都要分三类记 token。
  • 计划 105 到 120 次 agent 运行；额度不够按削减顺序砍。

13.1 10/26 闸门：AHa-3D 能不能无人值守跑完

"无人值守"指一次运行从开始到出 .blend，中间没有任何人插手。AHa-3D 的审查门、Stop hook、路径问题都可能让它卡住。

  1. 问题。10/26 中期检查时，A0、A1 能不能在 3 个开发场景上无人值守跑完？
  2. 能：交第一批数字，按计划进入主实验。训练加分项做不做也在这天定。
  3. 不能：给 harness（包在模型外面的工具和规则）打补丁。比如审查步骤改用转发 shim，放宽 Stop hook（agent 想停下时触发的检查）。
  4. 补丁的规矩：对包括 A0 在内的所有组完全一样，写进报告，结论里称"打过补丁的 AHa-3D"。
  5. 砍掉 A4：按我们的理解，修补丁花掉的时间和额度从 A4 里出。
  6. 禁止人工干预：不管卡在哪，运行中都不许人去点"继续"、补一句提示或手改文件。
容易搞错 · 打补丁和人工干预差在哪
  • 补丁是一段代码改动，每次运行、每个组都一样，别人拿到我们的补丁能复现同样的结果。
  • 人工干预是人在某一次运行里临时出手，每次出手的时机和内容都不一样，没法复现，也没法和别的组公平比较。
  • 所以补丁可以，干预不行。这是设计文档"我自己定的"第 12 条。
为什么不太担心

之前用 Haiku 5.5 跑通过一次 office48，用了 67 轮。真跑不完，退路是给 harness 打补丁，所有组用同一份补丁；除了砍掉加分的 A4，其余实验组一个不减。

大白话

14.1 路由小分类器长什么样

它的输入是六个数（或向量），输出是二选一。关键限制是：只能用推理时拿得到的特征，真值一概不能当输入。

六个特征 → 小分类器 → 生成还是方块
  1. 四个"看一眼就有"的特征。最好那一帧里掩码占多少像素、在几帧里看得见、估计的尺寸、类别文字的嵌入向量（把"杯子"这类词变成一串数）。前三个来自清单和感知结果。
  2. 两个"做完才有"的特征。SAM 3D 生成时给出的置信度，以及用方块摆好后的剪影 IoU（方块投到图上的轮廓和真实掩码重合多少）。
  3. 拼接。六个特征拼成一个向量。数值特征一般要先标准化，文字嵌入是一串数，直接接在后面。
  4. 小分类器。设计文档只说"路由小分类器"，没定结构。小 MLP 这类几层的小网络就够了，具体在执行时定。
  5. 输出二选一。用生成的网格（SAM 3D 生成再配准），还是用方块（就是清单里那个框本身，由代码搭出来）。
  6. 容易忽略的一点（按我们的理解）。特征 ⑤⑥ 要先把生成版和方块版都做出来才拿得到，所以分类器是在两样都做完之后挑一个。它替代的是 agent 的判断，省 token，不省生成的算力。
容易搞错

训练时手里有真值，很容易顺手把"离真值框多远"之类的量塞进特征。那样训练集上会很准，测试时却拿不到这个特征。设计文档的要求是"只用推理时拿得到的特征"，六个特征都满足这一条。

14.2 标签和训练数据从哪来

标签回答一个问题：同一个物体，方块和生成的网格，谁摆得更准？准不准对照真值框来判。

算例 · 大概有多少样本、要多少 GPU 时间（估算）
  • CA-1M 每个视频约 125 个框。85 × 125 = 10,625，这是真值框数的上限；去掉结构件、再看清单检出多少，实际样本会更少。

  • 训练用的 85 个视频不能和主实验的 22 个重叠，否则分类器在测试场景上"背过答案"。

14.3 怎么评：A3c 和 A3r、A3v 比

17术语表

全页出现的专有名词，按它们在流程里第一次出场的位置排列。先看下图找到术语属于哪一段，再查表里的白话解释。

术语白话解释
位姿（外参）相机在房间里的位置和朝向，每一帧一个。Pi3X 从视频里估出来。
内参镜头本身的参数：焦距和画面中心。它决定一个 3D 点投到图上的哪个像素。
点云 / 点图点云是一堆 3D 点。点图是"每个像素对应一个 3D 点"的图，和照片一样大；SAM 3D 要的 pointmap 就是它。
米制单位真的是米。单目视频估出来的尺度只是近似米制，所以评测时要用相机轨迹把尺度对齐。
MIG 切片把一张 GPU 切成几张互不干扰的小卡。Betty 上有 45 GB 和 90 GB 两种，不支持 OpenGL 和 Vulkan。
掩码标出某个物体占了哪些像素的黑白图。
清单待建物体的列表，每项一个 3D 框加一张 2D 裁剪图。A2 起交给 agent 逐项处理，评测时也用它判断"检测到"。
OBB（有向包围盒）包住物体的长方体，由中心、长宽高、朝向描述。清单、真值、评测用的都是它。
7 / 9 自由度描述一个框要几个数。9 个是中心 3 + 尺寸 3 + 任意旋转 3；7 个是只绕竖直轴转（旋转只剩 1 个）。CA-1M 的标注是 9 自由度，评测时转成重力对齐的 7 自由度。
高清帧Pi3X 用的那 32 帧换成 1024×768 的原图。位姿和深度仍然来自 Pi3X，所以只多了分辨率，帧还是那些帧。
同源 / 污染被测模型训练时见过测试数据或同一来源的数据，成绩会偏乐观。Boxer 训练时用过 CA-1M 训练集，所以每张表都放干净对照。
agent会自己调用工具、看结果、再决定下一步的大模型程序。像装修队的包工头：会看图纸、会叫师傅，自己也动手。
harness包在模型外面的那一层：提示词、工具、检查规则、什么时候停。AHa-3D 本质上就是一个 harness。
驱动模型agent 背后实际做判断的大模型。主实验是 GPT-6（经 Codex CLI），复跑用 Claude Opus 5.5。
token大模型读写文字和图片的计数单位。一次运行用了多少 token，决定它花了多少钱。
bpyBlender 的 Python 接口。agent 写的建模脚本就是 bpy 代码。
规范空间生成模型输出网格时用的标准姿势和单位大小，和房间里的真实位置无关。Hunyuan3D 的输出在这里，要配准才能放进场景。
配准 / ICP配准是把模型挪、转、缩放到和观测对上。ICP（迭代最近点）是经典做法：反复"找最近点、算变换"，需要一个不太差的初值。
剪影 / 剪影 IoU剪影是模型投到图上的轮廓。剪影 IoU 是它和真实掩码重合部分占两者合并部分的比例，越接近 1 越贴合。
验收门place_mesh 的最后一关。剪影 IoU、Chamfer 距离、尺寸三项都过，才保留生成的网格，否则退回方块。
Sim(3) / UmeyamaSim(3) 是"旋转 + 平移 + 统一缩放"的整体变换；不缩放的版本叫 SE(3)。Umeyama 1991 给出了从对应点直接算 Sim(3) 的公式。我们用它把 Pi3X 的相机轨迹对齐到真值轨迹。
匈牙利匹配预测物体和真值物体一对一配对、让总代价最小的方法。每个真值最多配一个预测。
IoU3D / d̂IoU3D 是两个 3D 框重叠体积除以合并体积。d̂ 是中心距离除以真值框的半对角线长，小物体上比 IoU3D 稳。
召回 / 精确率召回：真值物体里有多少被建好了。精确率：建出来的物体里有多少对得上真值。
漏斗记录每个真值物体最远走到哪一关：看得见 → 检测到 → 建出来 → 摆准了。像安检通道的几道关，看人在哪一道被拦下。
bootstrap按场景有放回地反复抽样、重算结果，看结果能波动多大，从而给出 95% 置信区间。
帕累托前沿在成本和精度上没被别的方法同时打败的那些方法。结论写成这条线，不写"哪种最好"。
消融只去掉或换掉一个部件，看结果变多少，以此判断这个部件的贡献。比如高清帧消融只改分辨率。
API 等价美元订阅不按次收费，就把每次运行的 token 数按官方 API 价格换算成美元，当作成本轴。
