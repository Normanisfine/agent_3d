## 0. 一句话

以 AHa-3D 为基线，第一次定量测出"视频转 3D 的 agent"在小物体上丢了多少、丢在哪一步；再在同一套流程、同样预算下，比较几种处理小物体的方式，给出成本-精度的权衡。

## 1. 为什么做这个

- AHa-3D（博客加开源仓库，GPT-6 Astra 驱动）把一段房间视频变成 Blender 场景，但**一个定量数字都没公布**。博客里演示用的任务描述写的是 "approximate small objects"（出自一次对比实验，不一定是发布版的默认提示词）。小物体来自一个 108 项的资产库，里面没有杯子、书、显示器。作者试过 SAM 3D 和 TRELLIS.2 生成物体，做完后又搁置了（01 号笔记）。
- 2026 年 9 到 10 月出了一批同类工作：GRASE、LIVIN（2610.12069）、GATOR（2610.11215）、LiteReality-Agent（2610.01863）、CoDimRecon（2609.36024）、HARMONY（2609.26793）。它们都用到了"小物体或难建的物体交给生成模型"，**所以这个做法本身不是我们的贡献**。
- 还空着的位置：
  1. 在"单目视频 → 整个房间 → agent 建模"这个设定下，没有人按物体大小报告召回和摆放精度（LIVIN 只对非 agentic 方法、在给定真值掩码和深度的条件下评过一档小物体）。
  2. 没有人把损失拆到流程的每一步（看不见、没检测到、没建、没摆准）。
  3. 没有人在同一套流程、同样预算下比较几种小物体处理方式。GATOR 只在物体级（每个物体 1 到 10 张图）比过分支。
  4. 没有人给出场景级的成本-精度曲线。
- GATOR 给 GPT-6 每个物体 10 分钟从零建模：ScanNet++ 上 CD 0.033，生成后精修 0.031，差得不多；但桌面小物体上是 0.016 对 0.009，差了将近一倍。**整间房、固定预算下生成划不划算是待检验的问题，不是前提。**

## 2. 目标、非目标、反目标

**目标**
- G1：AHa-3D 在真实数据上的第一份定量结果，按物体大小分档。
- G2：漏斗分析。每个真值物体走到哪一关丢的：看得见 → 检测到 → 建出来 → 摆准了。
- G3：在同一套流程、同一份感知结果、同样预算口径下，比较 P0、A0–A3v（第 5 节）的小物体召回和摆放精度，以及成本。
- G4：大家具（L 档）不比 AHa-3D 原版差。
- G5：2 到 3 段自己拍的房间视频，展示最终的 Blender 结果（定性）。

**非目标**
- 不训练主线模型。训练只是加分项（第 10 节）。
- 不量化形状和外观的好坏。CA-1M 只有框，形状只做定性展示；ScanNet++ 批下来了才补形状指标。
- 不做动态物体、人体、室外。
- 不重新实现 GRASE 或 GATOR 的全部系统，只借它们的做法（GATOR 式精修、GRASE 式剪影搜索）。

**反目标**（技术上跑通了也算失败的情况）
- 实验组之间的差距小于同一组跑两次的差距，却写成了"某组更好"。
- 用被评测的物体去做对齐，把要测的误差抵消掉了。
- 看了测试集结果再去调阈值或提示词。
- 把 Boxer 在 CA-1M 上的结果当成泛化能力来报。它训练时用过 CA-1M 的训练集。

## 4. AHa-3D 流程，以及我们怎么拆它

AHa-3D 的阶段（详见 `CIS-6220.../03-final-project/agentic-3d/notes/deep-aha3d.json`）：

1. **Observe**：Pi3X 估相机和点云，SAM 3 分割结构类，RANSAC 拟合地面和墙，做 TSDF，生成参考视角图。
2. **Measure**：agent 在帧上挑像素点量尺寸。
3. **Build**：agent 用 RoomKit 写 bpy 脚本，用方块、程序化柜子和资产库搭场景。
4. **Verify**：X-Ray 轮廓叠加、source_fit（掩码 IoU、边界距离），加物理检查（碰撞、支撑、稳定）。
5. **Gate**：Codex 只读审查员给出 accepted 或 rejected。

我们把它归成四个环节：**找物体 → 建形状 → 摆准 → 检查**。所有改进都落在这四个环节里。

**所有实验组共享的东西**（保证比较公平）：
- 每个场景的 Pi3X 和 SAM 3 参考结果只在 Betty 上**算一次**，按作者默认的 25.5 万像素和 32 帧。所有实验组读同一份，感知的随机性就不会混进组间差异。
- 同一个 AHa-3D 版本（提交 82f4b11，或者我们 fork 后的固定提交）、同一个 Blender 5.2.1、同一个驱动模型、同一个推理强度。
- 可开合柜子、物理检查、审查门这些功能在所有组里保持原样。

## 7. 驱动与成本

- **主实验**：Codex CLI 用 ChatGPT 订阅登录，驱动 GPT-6；订阅里有 Astra 就用 Astra，没有就用 Sol。这是 AHa-3D 原生的驱动方式，最接近复现作者的设置。
- **开发调试，以及 5 个场景的复跑**：headless Claude Code（Max 订阅），用 Opus 5.5。AHa-3D 的审查步骤写死了 `codex exec`，在 Claude 那边要用一个转发 shim，之前的会话里做过。
- **10-27 改动（Yifan 定）**：主实验改用 headless Claude Code（Max 订阅）驱动 Opus 5.5，推理强度固定 medium，和我们自己的 Claude 环境隔开（不读用户设置、不用技能和 MCP、关自动记忆和 Artifact）；AHa-3D 内部的审查仍调 `codex exec`。每次运行从 stream 的 rate_limit_event 记订阅的 5 小时和每周使用率。先在开发场景量一次花费再排队。
- **10-27 实测与排程**：开发场景 A0 一次 113 分钟、263 次工具调用，5 小时窗口约 +14 个百分点、每周约 +1 个百分点（同一窗口里还有我们自己的会话）。按顺序跑完测试集 50 次要 100 小时左右，所以分两条线同时跑（`LANE=b`）：一条跑测试集的 A0/A1，另一条先跑开发场景的 A1–A3v、检查过工具再跑测试集的 A2/A3r/A3v。两次运行同时跑时本机基本空闲（时间都花在等模型），所以对结果没有影响，但墙钟时长只作参考。AHa-3D 自带的图像审查每次最多 600 秒（`review_contract.py`，原版就有），超时算没审过，我们不改。
- **10-27 审查统一（19:30 起）**：AHa-3D 调审查时不指定模型，于是用各账户 `config.toml` 的设置：`~/.codex` 是 gpt-6.1-sol + ultra，`~/.codex-b` 没设（用默认）。ultra 审几百张图很快把 Plus 账户的 5 小时窗口用完（开发场景 A2、测试集 A0 42897538 都碰到"usage limit"，有的审查没跑成）。现在 `.runtime/bin/codex` 指向 `scripts/codex_review.sh`：exec 调用固定 gpt-6.1-sol + medium（和 Codex agent 一致），某个账户额度用完就换下一个重试。不改全局的 `~/.codex/config.toml`。之前的运行（旧 Codex 对照组和 10-27 19:30 前的 Opus 运行）审查强度随账户不同：对照组 17 次里 3 次在 `~/.codex`、3 次在 `~/.codex-b`、11 次没记账户。
- **10-27 进程隔离（20:20 起开跑的运行）**：两条线同时跑时，测试集 A1 42897538 的 agent 执行了 `pkill -f "codex exec --ephemeral"`，会把另一条线正在跑的审查一起杀掉（这次另一条线恰好没有审查在跑）。现在每次运行的 agent 都在自己的 PID 命名空间里（`unshare --user --map-current-user --pid --fork --mount-proc`，同一 uid，文件、GPU、网络不变），只看得到、也只杀得到自己的进程；agent 结束时它留下的后台进程一起结束。之前的运行没有这层隔离。
- **10-27 生成预算按候选计（20:45 起）**：生成结果按（帧、掩码、后端、种子）缓存在 `gen/<场景>/`。之前缓存命中不扣预算，同一场景先跑的 A3 组生成、后跑的组白拿，A3r/A3v 的对比会随跑的先后偏。现在每次运行的 30 个预算按它拿到的不同候选计，新生成的和缓存来的一样扣；已经拿到的候选再要不扣，失败后重新生成照扣。缓存只省 GPU 时间。开发场景 A3r（47331262）是旧规则下跑的，用了 P0 留下的缓存（只用于检查工具，不进结果）；测试场景在这之前没有缓存。

## 9. 评测

### 9.1 预测物体从哪来
从最终的 .blend 里导出每个语义根节点（AHa-3D 的 `export_model.py`，按 instance_id 分组）的世界坐标有向框。P0 直接用它自己的输出。

### 9.2 对齐
- 主口径：把 Pi3X 的相机中心和 CA-1M 注册过的相机中心对应起来，做 Sim(3) Umeyama，加重力约束。**不用被评测的物体来对齐。**
- 同时报一个不修正尺度的版本（SE(3)，尺度固定为 1），用来体现 Pi3X 自己的尺度误差。
- VSI 开发集和 BVB 重新打分时没有相机轨迹，只能用 L 档家具加地面来对齐，并且只给 XS、S、M 三档打分，表里注明。

### 9.3 尺寸分档
按真值框的最长边分：**XS 小于 0.2 m，S 0.2–0.5 m，M 0.5–1.5 m，L 1.5 m 以上**。每档都报真值物体的数量。

### 9.4 匹配和三种结局
- 用匈牙利算法一对一匹配，不看类别（CA-1M 有 48% 的框类别只写了 "object"）。代价是按大小归一化的中心距离 d̂ = ‖c_pred − c_gt‖ / r_gt，其中 r_gt 是真值框半对角线长。
- 宽松门槛另加尺寸条件：最长边之比在 1/3 到 3 之间；配对代价 = d̂ + |log(最长边之比)|。（10-23 在开发集上发现：没有尺寸条件时，柜子里的一本书会被配给柜子，还把书从书的真值那里抢走。这是协议漏洞的修正，不是按结果调阈值；测试集当时一次没跑。）
- 两套判据**分开报**：
  - 判据 I：IoU3D ≥ 0.25（另报 0.5），方便和前人比较。
  - 判据 D：d̂ ≤ 0.5，并且最长边之比在 0.67 到 1.5 之间。
- 每个真值物体归为三种结局之一：
  - **建好了**：通过严格判据（I 或 D，各报一张表）。
  - **建坏了**：没通过严格判据，但在宽松门槛内（d̂ ≤ 1.0，或 IoU3D ≥ 0.1）。
  - **漏了**：连宽松门槛都没进。
- 精确率作为次要指标报（多建出来、匹配不上真值的物体）。因为 CA-1M 是穷举标注，这个数有意义。
- 以上阈值都是**我们定的初值**。10/20 之前还没有任何 agent 运行，所以只在开发集上用两样东西做合理性检查：真值对真值（应全部"建好了"），以及检测器直接输出（Boxer 和干净对照的框）对真值的分布。不拿任何 agent 组的输出来调阈值。10/20 前写进 `configs/thresholds.json` 定死。
- **G1 冻结（10-27，Yifan："评测标准按照你的来"）**：测试集打分前定死，之后不再改，`configs/thresholds.json` 打了 git 标签 `protocol-frozen`。
  - 认可 10-23 的两处修正（尺寸条件、真值去门窗踢脚线和壳体零件）和 10-24 的地毯豁免。它们是看过开发集 A1 输出后定的，报告里如实写明。
  - 配对改成**按代价从小到大贪心**（`match_mode: greedy`），不再为了多配一对把"建好了"拆成两个"建坏了"。
  - 判据 D 的距离条件加 **10 cm 下限**（`strict_floor_m: 0.10`）：d̂ ≤ 0.5 或中心距离 ≤ 10 cm 都算。XS 原来的容差（约 4 cm）和相机对齐误差（2–4 cm）差不多大。
  - 宽松门槛另加 **30 cm 绝对门槛**（`loose_abs_m: 0.30`）：中心距离 ≤ 30 cm（且尺寸比在 1/3–3 之间）也算"建出来"。原来的相对门槛会把偏了 15 cm 的杯子记成"没建"。
  - 报告里另给"G1 之前的口径"作对照（`results/checkpoint/funnel_pre_g1.png`、`sensitivity.md`）。

### 9.5 漏斗（主图）
每个真值物体记录它最远走到哪一关：
1. **看得见**：在**该组实际用到的帧**里（都是 Pi3X 那 32 帧），用 CA-1M 的激光深度判断遮挡后，至少有一帧里可见面积 ≥ 100 像素（约 10×10）。A0、A1 按流程分辨率（约 574×434）算；P0、A2、A3、A4 在这 32 帧的 1024×768 原图上找物体和裁剪，按原图分辨率算。漏斗图里另画一条"流程分辨率下看得见"的参考线，两者之差就是高清帧带来的空间。
2. **检测到**：清单里有一个框在宽松门槛内匹配上它。只有带清单的组有这一关（P0、A2、A3、A4）；A0、A1 跳过。
3. **建出来**：最终场景里有物体在宽松门槛内匹配上它。
4. **摆准了**：通过严格判据。

每个实验组、每个尺寸档画一根堆叠条形。"看得见"这一关不用调大模型，算出来就是"不管 agent 多聪明都过不去的天花板"。

### 9.6 统计
- 组间比较时，同一个真值物体在不同组的结局两两配对，按场景做 bootstrap，给出 95% 置信区间。
- A1 和 A3v 在 5 个场景上的第二次重复，用来估计同一组跑两次的差异有多大。组间差距比它小的，不下结论。
- 结论写成"成本-精度的帕累托前沿"，不写"哪种最好"。

### 9.7 成本
每次运行记录 token 数（输入、缓存、输出）、按 API 价折算的美元、墙钟时间、fal 费用。

| Boxer 同源导致 A2 偏乐观 | 每张表都放干净对照，并标注。10-26 核对：我们 22 个场景都在 CA-1M val（107 段）里，Boxer 训练只用 train，没见过它们；但它的 CA-1M 测试集是"val 前 10 段"，按官方 `data/val.txt` 的文件顺序算包含我们测试集的 47115543，按编号排序算包含 42897538、42897647（也都是测试集）。作者可能看过这几段的结果，报告里注明 |
| Pi3X 的前身 π³ 训练时用过 ARKitScenes 和 ScanNet++（π³ 论文 §3.4），CA-1M 的视频就是 ARKitScenes；Pi3X 本身的训练集是否相同未核实 | 几何精度的绝对值可能偏乐观，报告里注明；所有实验组共用同一份感知结果，组间比较不受影响 |
| fal 上 SAM 3D 的位姿坐标约定不明 | 第 1 周在 fal 上拿 5 个物体核对（10 美元上限之内） |
| Betty 上的 SAM 3D 在 11/2 前装不通（HF 审批慢，或 B200 的 sm_100 环境问题） | 正式实验改用本地 Hunyuan3D-2mini 加我们的配准，报告里注明；训练加分项不做 |
| Betty 计算节点不能上网 | 权重在登录节点预先下载，计算作业离线跑；Colab 备用 |
| 本地硬盘只剩 65 GB | 不下 .mov；权重和中间结果放 Betty；本地只放评测数据和最终的 .blend |
| 两个月内有人发表同样的评测 | 提案和报告里写"据 2026-10 的检索"，把贡献落在漏斗和公平比较上 |

## 15. 我自己定的（用户可以否决）

1. A3r 的规则：估计最长边小于 0.5 m 的物体走生成。
2. 验收条件：剪影 IoU 要比方块版高 0.03 以上，另加 Chamfer、尺寸、穿进支撑面三项条件。
3. A4 每个物体最多精修 3 轮。
4. "建坏了"的宽松门槛：d̂ ≤ 1.0 或 IoU3D ≥ 0.1；"看得见"的门槛：可见面积 ≥ 100 像素。
5. 感知结果每个场景只算一次，所有组共享。
6. 输入视频用 CA-1M 的帧合成，10 fps。
7. 22 个视频用固定种子分成 5 个开发、15 个测试、2 个备用。
8. 自拍视频的规格：手机横拍，30 到 60 秒，一个镜头到底。
9. "高清帧" = Pi3X 那 32 帧的 1024×768 原图，位姿和深度都来自 Pi3X，真值传感器数据不进流程。
10. "同样预算" = 所有组同一个墙钟上限和轮数上限，加失败重跑一次的规则，各组失败率单独报。
11. 干净对照只在"检测到"这一关比较，外加 P0 跑两种清单；agent 组不重跑干净版。
12. 10/26 的退路是给 harness 打补丁（所有组一样），不是人工干预。
